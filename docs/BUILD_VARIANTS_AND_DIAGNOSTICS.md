# Две сборки Kord Rotation — каноническая архитектура и план приёмки

**Статус:** УТВЕРЖДЕНО ЗАКАЗЧИКОМ 2026-11-21; нормативное решение для всех будущих чатов. **Тип изменения:** сначала документация; исполнение и игра отдельно. **Основа API:** [Canonical API Matrix v14](rotation/Canonical_API_Matrix.md), WoW Forever 1.60.1.71037 как исследованный экспорт Blizzard, CLIENT PASS = 0/101. Матрицу не подгонять под старый код. **Приоритет:** настоящие [AGENTS.md](../AGENTS.md) и [Kord Rotation Creation Guide](Kord_Rotation_Creation_Guide.md), правило №1 предварительного сравнения/одобрения остаётся действующим.

## Одно ядро и два физических аддона

| Поставка | WoW AddOn-папка и TOC | Назначение | Включение диагностического кода |
|---|---|---|---|
| **Пользовательская** | `Interface/AddOns/KordRotation/KordRotation.toc` | Каноническое чтение API, GameData, Engine, Profiles, рекомендационный UI, обычные безопасные функции | **Нет** `KordRotationDevTools` в пакете, нет developer-кнопок/записи/тяжёлых probe/trace; не добавлять условную скрытую кнопку в пользовательскую UI |
| **Диагностическая** | Те же файлы `KordRotation` **без изменения байтов ядра** + `Interface/AddOns/KordRotationDevTools/KordRotationDevTools.toc` | Всё пользовательское ядро плюс ручные инструменты исследований API, трассировки ротации, мониторинга событий и производительности | DevTools — отдельный аддон с `## Dependencies: KordRotation`; свой код, локализация и SavedVariables; пользователь намеренно устанавливает оба |

**Не создавать вторую копию ядра и не поддерживать разные боевые алгоритмы в двух сборках.** `KordRotationDevTools` наблюдает за утверждёнными точками диагностики общего ядра; оно **не** подменяет API, не обходит Secret API и не меняет приоритеты. Совпадение SHA общих файлов в двух пакетах должно проверяться сборочным тестом. Папки и TOC DevTools **предложены и утверждены как целевая структура, но пока не созданы**; нельзя объявлять их существующими. Существующие `Core/Diagnostics.lua` и `UI/Pages/AdvancedDiagnostics.lua` — **историческая базовая диагностика интерфейса**, а не новая Developer Tools. Их граница миграции требует отдельной инвентаризации: в продукте могут остаться только полезные пользователю безопасные сведения (например, версия и поддержка), но кнопки developer probe/trace должны переехать в DevTools. Ничего не удалять без проверки зависимостей/локализаций/сохранённых данных.

## Источники истины без дублей

1. **Что API разрешено и насколько подтверждено:** только `docs/rotation/Canonical_API_Matrix.md` v14, 101 строка, 58 исходниковых подтверждений + 20 частичных + 23 открытых; **0 игровых PASS**. Если ошибка матрицы — отдельно задокументировать доказательство/номер строки и согласовать изменение.
2. **Какие нормализованные GameData-поля получает профиль:** `docs/rotation/GameData_Contract.md` после утверждения соответствующей схемы; не выдавать сейчас список кандидатных полей за уже реализованный контракт. Не строить временные runtime-адаптеры старых ротаций.
3. **Что делает конкретный профиль:** `docs/rotation/Profile_Registry.md` (статусы), `Priority_Matrix.md` (приоритеты), `Ability_Catalogue.md` (доказательства), `Configuration_Registry.md` (CFG), `Research_Evidence.md` (источники), `Test_Matrix.md` (сценарии). Ротационный стандарт — единый `docs/Kord_Rotation_Creation_Guide.md`.
4. **Какие файлы реально установлены и загружены:** Git-дерево, `.toc` и проверяемые артефакты сборки, не нормативные документы. **Наличие файла профиля ≠ подключённый профиль ≠ внутриигровой PASS.**
5. **Процесс и очередность:** этот документ и `docs/ROADMAP.md`; `AGENTS.md` ссылается сюда. Старые разделы «первый Воин», «один пакет» и «диагностика только внутри KordRotation» больше не являются действующими планами; старые релизные и CHANGELOG-отчёты — история версии, не новые требования.

## Фиксированный порядок разработки

**Шаг I — каноническое ядро v14.** Выполнить утверждённую работу 2.8.1–2.8.6, начиная с полного построчного аудита 101 API-возможности, затем GameAPI/GameData, AbilityEligibility, RotationEngine/RotationProfiles, BindingResolver/EventBus/UI, интеграция и регрессия. **Без runtime-адаптеров для старых профилей.** Встроить безопасные неизменяющие ход боя точки наблюдения для DevTools. Обновлять docs/rotation реестры и CHANGELOG в каждом коммите; проверять HEAD перед записью. При непроверенном API — UNKNOWN/NOT VERIFIED, без fail-open.

**Шаг II — DevTools.** Создать второй физический аддон, а не конфигурацию `debug=true` внутри одного пользовательского пакета. Инструменты ручного начала/остановки сеанса; API-probe по v14; выборочные EVENT/ENGINE/ELIGIBILITY/PROFILE/ERROR/Performance trace; экспорт и очистка. Уровни ERROR/NORMAL/TRACE; ограничение частоты, объёма и числа записей; отключено по умолчанию; никакого фонового тяжёлого трассирования без согласия пользователя. Все новые UI-элементы в отдельном аддоне локализовать на шесть языков.

**Шаг III — одна пилотная ротация:** `KordRotation/Profiles/Hunter/Kord_Hunter_BM_Leveling_PVE.lua`, **Охотник BM 1–59, PvE**. Перенести вызовы и поля на новый контракт ядра **без изменения исходных приоритетов, ST/AoE, кулдаунов, CFG, pet-поведения и игрового стиля**, насколько это доказуемо; каждый вынужденный из-за UNKNOWN или несовместимости дрейф поведения документировать, не скрывать. Другие BM 60, MM, SV, PvP и Воин **не являются пилотом**. Никакого автоматического включения остальных черновых Hunter-профилей. При переносе обеспечить дифференциальные тесты с одинаковыми достоверными игровыми состояниями.

**Шаг IV — игровой QA на диагностической сборке:** сначала проверить API в актуальном Forever клиенте, затем BM 1–59: смена уровня, отсутствие питомца/смерть/призыв, Auto Shot и движение, цель/дистанция, GCD/charges, ресурсы, ST/AoE, solo/world/dungeon/raid когда доступно, угроза/Feign Death, секретные значения, смена цели/спека, инвалидация/верность биндов. Привязывать каждый результат к номеру v14 и реальному событию; без игрового теста ставить NOT RUN. Обнаруженные проблемы разбирать по собственному журналу и повторять сценарии.

**Шаг V — отдельная пользовательская сборка:** проверять отсутствие DevTools в пакете, отсутствие developer-кнопок и диагностических SavedVariables, отсутствие необязательной зависимости от DevTools, функциональный паритет ядра, чистую установку и пользовательские настройки. Выпуск только после соответствующей приёмки.

## Контракт диагностического сеанса

- **Явный opt-in:** пользователь вручную нажимает «Начать запись», затем «Остановить». Можно запускать отдельный безопасный разовый API-пробник; никакого автозапуска трассировки после установки или /reload.
- **Метаданные:** версия Kord, версия DevTools, идентификатор commit/build (из упаковки), версия матрицы v14, `GetBuildInfo`, дата/локальное время, идентификатор сценария. Не выдавать Git SHA из .toc или текущую ветку за известные данные, если build pipeline не встроил их.
- **Событие:** локальный monotonic timestamp/порядковый номер, модуль, event/method, **номер v14**, статус READY/BLOCKED/UNKNOWN/UNAVAILABLE/ERROR, machine-readable reason, время вызова/счётчик; безопасный контекст только по allowlist. Для профиля — идентификатор, phase, spell candidate, приоритет, причина принятия/отклонения и изменение рекомендации.
- **Secret safety:** не сериализовать secret или tainted объекты, сырые frame/unit GUID/имена игроков, чат, содержимое боевого журнала, токены или ошибки целиком; нельзя вызвать `tostring`, сделать сравнение или table key от секретного значения до проверки безопасности. Зафиксировать лишь `protected_value` / статус и контролируемое имя метода.
- **Ошибки и нагрузка:** `pcall` вокруг безопасных read-only методов только; не пробовать защищённые combat actions. Ограниченный кольцевой буфер, dedup/rate limits, счётчики отброшенных записей, контролируемый объём SavedVariables, измерения без тяжёлого OnUpdate. При переполнении показывать dropped count вместо бесконечного роста.
- **Экспорт:** в игре данные живут в памяти; при `/reload`/корректном выходе SavedVariables сохраняются, либо пользователь копирует выделяемый/постраничный текст вручную. Lua-аддон не пишет произвольные текстовые файлы и не отправляет данные наружу. DevTools SavedVariables отдельные от `KordRotationDB`. Сеансы логируются только после явного включения.
- **Тесты:** чистая пользовательская сборка (без DevTools), диагностическая сборка (оба аддона), одиночный сеанс, большой объём/overflow, секретные поля, отсутствующий API, ERROR, Ctrl+C/копирование, /reload persistence, сравнение SHA ядра и CPU/RAM. Само наличие API или `pcall` != доказательство корректного игрового результата.

## Что запрещено объявлять завершённым сейчас

Ни DevTools, ни переведённое ядро v14, ни новая интеграция BM 1–59, ни real-client PASS не реализованы только потому, что написана эта спецификация. Сохранить ранее опубликованные mock-тесты как историю, но **не** переносить их PASS на новое ядро. До открытия новой ветки изменений соблюдать правило № 1 и согласованный объём без дополнительных самовольных функций.

## Противоречия, которые нужно поддерживать закрытыми

- **Один устанавливаемый аддон / DebugToggle в продакшене:** заменить на **два физически разных аддона** + одно ядро.
- **Пилот Воин — Оружие или Hunter 60:** заменить на **Hunter Beast Mastery Leveling PvE 1–59**.
- **Сначала один пользовательский релиз, потом только диагностика:** заменить на **ядро → DevTools → пилот → игровой QA → пользовательская сборка**.
- **Скрытые runtime-адаптеры старых ротаций:** запрещены; переносить профили на контракт нового ядра.
- **58 подтверждённых методов = 58 игровых PASS:** неверно. Все 101 CLIENT PASS остаются 0 до игрового теста.
- **Произвольные логи в каталоге WoW или автосбор с клиента:** запрещены; только разрешённые SavedVariables/ручной экспорт.
- **Два каталога классовых правил для двух типов сборки:** запрещены; один реестр и один исходный код профилей.
