## Findings: исправить до 2.5

### P1 — доступ к защищённым таблицам не закрыт полностью
- **Где:** `Core/GameAPI.lua`: `Read`, `ReadValues`, `secret`; `Core/SpellCatalogue.lua`: `safeField`.
- **Доказательство:** Kord проверяет `issecretvalue`, но не использует предусмотренный клиентом `issecrettable`/`canaccessvalue`; Sonah `Core/Atoms/Secret.lua:12–35` явно различает secret-value и secret-table.
- **Риск:** структурированный `C_SpellBook` или другие API могут вернуть таблицы, чтение которых невозможно безопасно; в некоторых случаях даже проверка типа/поля небезопасна. Отсутствие функции обнаружения нельзя выдавать за гарантированную доступность.
- **Решение:** добавить единую безопасную проверку доступности таблицы/полей и контрактные тесты с mock secret-table. Любую неоднозначность переводить в `UNKNOWN`; не пытаться обходить защиту.

### P1 — неизвестные типы modern spellbook молча пропускаются
- **Где:** `Core/SpellCatalogue.lua`, `modern()`: ветка `elseif kind==nil then ...` после `if kind==spellType`.
- **Доказательство:** незнакомое ненулевое `itemType` не вызывает ошибку; цикл завершается с `status="ready"`. Legacy-путь при неизвестном типе более консервативен.
- **Риск:** частичный список выдается за полный; при смене схемы API пропадают способности.
- **Решение:** определить явный whitelist точно подтверждённых допустимых типов (future/прочие) конкретного клиента; неизвестные типы дают `unavailable/unknown_item_type`. Добавить mock-test с itemType=неизвестный код.

### P2 — не учтены известные не-книжные/пассивные способности
- **Где:** `Core/SpellCatalogue.lua`; сравнение Sonah `Core/Atoms/Spells.lua:171–188`.
- **Наблюдение:** Sonah отдельно проверяет `C_SpellBook.IsSpellKnown`/`IsPlayerSpell` для способностей, отсутствующих в обычных вкладках. Kord ограничивается обходом книги.
- **Риск:** неполнота будущего справочника профиля; **не** означает, что нужно автоматически допускать такие способности в ротацию.
- **Решение:** предусмотреть отдельный доказательный поиск известных Spell ID только для запрошенных профильных кандидатов; не генерировать все ID и не обходить жёсткое требование «должен быть slot Blizzard». Это можно реализовать вместе с 2.5/2.7 после подтверждения API.

### P2 — покрытие изменений и допустимость событий
- **Где:** `Core/EventBus.lua`, подписка `SpellCatalogue:Initialize`.
- **Доказательство:** в MaxDps `Core.lua:376–395` присутствуют `C_EventUtils.IsEventValid` и события `UPDATE_BONUS_ACTIONBAR`, `UPDATE_STEALTH`, `LEARNED_SPELL_IN_SKILL_LINE`, `PLAYER_SPECIALIZATION_CHANGED`; часть из них Kord ещё не отслеживает. Некоторые могут быть неактуальны в Forever.
- **Риск:** устаревший кэш и пропуск переобучения/смены формы. Kord пытается зарегистрировать часть событий с `pcall`, но это не является подтверждением, что событие реально приходит.
- **Решение:** матрица необходимых событий для 2.4/2.5, feature detection перед регистрацией при наличии `C_EventUtils.IsEventValid`, запасная инвалидация по загрузке/изменению состояния. Не регистрировать всё подряд просто потому, что MaxDps так делает.

### P2 — неоднозначность «пустая книга» и доверие к legacy
- **Где:** `Core/SpellCatalogue.lua`, `legacy()` при `tabs==0`.
- **Риск:** `GetNumSpellTabs()==0` сразу объявляется настоящей пустой книгой, без проверки готовности другого API/состояния загрузки. Если legacy вызов доступен, но возвращает 0 на несовместимом клиенте, modern путь не пробуется.
- **Решение:** считать нулевой legacy результат предварительным, проверить modern если доступен; `ready/empty` только когда клиентским контрактом подтверждена именно пустая книга.

## Findings: оптимизация, но не блокер

### P3 — лишняя работа при частых событиях
- `EventBus` имеет легковесный `OnUpdate` даже без подписчиков; `GameState:GetSnapshot` сравнивает dirty-ревизии и может пересчитываться чаще 0,20с, если запрашивается каждый кадр. MaxDps использует bucket events (`Core.lua:376`) и отложенный `Fetch`; Kord уже имеет коалесцирование, но **не гарантирует верхнюю частоту фактических чтений GameState**.
- **Решение:** при реализации живой ротации замерить частоту пересчётов и установить отдельный минимальный интервал работы дорогих адаптеров; избежать обработки без потребителей. Не оптимизировать вслепую сейчас.

### P3 — лишние таблицы и расширение whitelist
- `GameAPI:ReadValues` выделяет таблицу шести значений на вызов, `SpellCatalogue:Read` копирует весь кэш при каждом запросе и сканирует по TTL=2с. При редком обновлении книги это приемлемо, но не должно вызываться из ротационного `OnUpdate`.
- В `GameAPI` уже разрешены будущие методы `GetActionInfo`/`GetBindingKey`/прочие; это не загрузка библиотек и почти не влияет на вес, но при 2.5 следует ограничивать API действительно нужными адаптерами и тестировать аргументы/типы.

### P3 — разница политик рангов
- Sonah `Core/Atoms/Spells.lua:49–65` старается предпочитать актуальные высокие ранги, а Kord сохраняет каждую запись по spellID. **Текущий подход Kord оправдан для редактора всех известных рангов**, но будущий CandidateFilter должен явно выбирать валидный ранг и избегать устаревших.
- Modern-путь Kord использует более строгую проверку `Enum.SpellBookSpellBank.Player`/типов, чем fallback в Sonah. Это не ошибка: лучше `UNKNOWN`, чем неоговорённый enum; совместимость уточняется по клиенту.

## Что НЕ считать ошибками на 2.4

- Пока нет `ActionBarScanner` и `BindingResolver`: их реализация утверждена на 2.5/2.6.
- Пока нет полноценного применения `Eligibility`/аур/кулдаунов и ротационных профилей: этапы 2.7–3.
- Kord не должен перенимать макро-парсер, автокаст, сторонние зависимости или bulk-базы из MaxDps; это увеличило бы код и усложнило контроль доступности.
- Отдельные read-only модули и сохранение прежнего интерфейса — корректная архитектура.

## Рекомендованный порядок перед продолжением

1. **Корректирующий коммит 2.4a:** secret-table проверки, неизвестные modern itemType, неоднозначное пустое legacy и их mock-тесты.
2. **При 2.5:** учесть дополнительные события и feature detection, страницы/стойки/макросы, макросы без однозначного spell ID — пропуск; подготовить подтверждение существования слота Blizzard как обязательный gate.
3. **При 2.7:** проверка известных вне книги spellID по конкретному кандидату и фактическая usable/cooldown/range, не обходя требование Blizzard-панели.
4. **Перед объявлением статуса DONE:** реально выполнить автономные Lua-тесты и финальный WoW Forever QA; логировать PASS/FAIL/NOT RUN раздельно.
