# STAGE 02.3 — GameState: player, target, combat и ресурсы

**Версия:** 0.1.8.3-rc2. **Статус:** реализовано в Lua, подтверждение поведения внутри WoW Forever — NOT RUN.

## Архитектура

`Core/GameState.lua` предоставляет `Initialize()`, `Invalidate(reason)`, `ReadNow()` и `GetSnapshot()`. Состояния читаются только через ограниченный read-only `KR.GameAPI`. Возвращается независимая копия результата (изменение потребителем не меняет кэш). API ничего не нажимает, не рисует и не сохраняет приватные игровые значения в SavedVariables.

Снимок содержит `status`, `observedAt`, `revision`, `player`, `target`, `combat`, `resources`, `casting` и возможную `reason`. Каждое прочитанное поле использует контракт `{status=READY|UNKNOWN|UNAVAILABLE|ERROR, source, reason?, observedAt?, value?}`, разработанный в 2.1–2.2.

- `player`: подтверждение существования, GUID, класс (кортеж локализованного имени + classToken), уровень, здоровье, смерть, фактический бой, верховая езда.
- `target`: существует ли цель, GUID, здоровье, смерть, возможна ли атака/помощь, является ли самим игроком. Если цель достоверно отсутствует, статус `ABSENT`, зависимые поля не читаются.
- `combat`: раздельно `UnitAffectingCombat("player")` и `InCombatLockdown()`; при частичной недоступности общий статус `UNKNOWN`.
- `resources`: сначала `UnitPowerType`, затем `UnitPower` и `UnitPowerMax` для того же типа. Неизвестный тип не заменяется типом 0. Проценты только если максимум больше нуля.
- `casting`: отличает подтверждённые `CASTING`/`CHANNELING` от `UNKNOWN` (nil не трактуется автоматически как «ничего не кастует», пока клиентский контракт не подтверждён). Время начала/окончания кастов — отдельная будущая клиентская проверка.
- `health`: процент только для чисел с `0 <= current <= max`, `max > 0`. Неизвестный GUID, избыточное здоровье или защищённое значение не получают фальшивой READY-оценки.

`GameState.status=READY` означает лишь наличие минимально подтверждённых флагов существования игрока/цели и боевого состояния. Это **не** значит, что все вложенные поля доступны, заклинание применимо или есть действующий боевой движок. Каждый потребитель обязан сверять статус нужного конкретного поля.

## Инвалидация и время жизни

- `GameState` подписывается через `KR.EventBus` на `identity`, `target`, `combat`, `health`, `resources`, `cast`, `talents`, `heartbeat`.
- Добавлены события `PLAYER_ENTERING_WORLD`, `UNIT_HEALTH`, `UNIT_MAXHEALTH`, `UNIT_DISPLAYPOWER`, `UNIT_MAXPOWER`, `UNIT_FLAGS`. Фильтр по player/target сохраняется. Коды событий — кандидаты до верификации в игре.
- При запросе `GetSnapshot()` кэш пересчитывается, если было изменение revision, явный `Invalidate`, время прошло больше 0.5с или часы отсутствуют/пошли назад. Событийный callback лишь отмечает грязное состояние, не вызывает дорогие чтения непосредственно из `OnUpdate`.
- Нет подмены `UNKNOWN` на «ложь»; пользовательский интерфейс и режим тестовых иконок не менялись.

## Проверка и ограничения

`tests/stage_02_03_game_state.lua` — автономный Lua mock: отсутствие цели, подтверждённая цель, смена цели до/после Flush, здоровье выше максимума, secret GUID, недоступность типа ресурса, `UnitExists=nil`, отсутствие таймера и изоляция кэша. Запускать из корня репозитория через `texlua tests/stage_02_03_game_state.lua` либо совместимый Lua.

В игре проверить реальные значения `UnitPowerType`, `UnitGUID`, `UnitHealth`, `UnitIsUnit`, `UnitCanAssist` и регистрацию новых событий, особенно в бою и при смене формы. Без этого `GameState` остаётся **IMPLEMENTED / AWAITING IN-GAME QA**, а не 100% доказанной совместимостью.
