# CHANGELOG_RULES — обязательный стандарт истории изменений

**Применяется к КАЖДОМУ коммиту, включая правки документации, исправления, рефакторинг, настройки, сборки и откаты.** Ссылка на файл в `AGENTS.md` и `README.md` является частью протокола возобновления между чатами.

## 1. Что обязательно записывать
Для **каждого** коммита в `CHANGELOG.md` должна существовать самостоятельная подробная запись:
1. **Дата/время** в ISO 8601 с явно указанным часовым поясом (желательно UTC), ID записи `KR-YYYYMMDD-NNN`, релиз/этап, статус.
2. **Идентификатор коммита** (полный Git SHA, если известен, или стабильный идентификатор записи в заголовке/теле commit message и ссылка на Git-историю); при связи с ранее существующим коммитом указывать точный SHA. Задача / Issue / PR и отчёт тестировщика.
3. **Контекст:** какая проблема/потребность/несовпадение, ожидаемое и фактическое поведение, где наблюдалось, точные шаги воспроизведения, версия WoW Forever/класс/ветка (если применимо).
4. **Причина:** анализ первопричины с доказательствами. Неизвестную причину так и помечать; гипотезы не выдавать за подтверждение.
5. **Изменения:** конкретные файлы, функции, настройки и логика, что и зачем изменено, почему выбран именно этот способ, возможные побочные эффекты.
6. **Проверки:** какие действия выполнял разработчик, тестовая среда, результаты PASS/FAIL/NOT RUN с объяснением отсутствующих проверок.
7. **Выдано пользователю/тестировщику:** ссылка на коммит/PR/архив, инструкции установки/воспроизведения и что конкретно проверить.
8. **Результат и статус:** что стало работать, что ещё неизвестно, остаточные риски, требуемая обратная связь, следующий шаг.
9. **Связи:** номера предыдущих фиксов, Issue/PR, регрессии, ссылки на новый/старый коммит.

## 2. Специальное правило: тестер обнаружил ошибку
При тестовом отчёте ОБЯЗАТЕЛЬНО:
- Создать/идентифицировать задачу `BUG-... / GitHub Issue #...`; если Issue не создан, использовать локальный `BUG-YYYYMMDD-NNN`.
- Зафиксировать кто проверял (например «пользователь»), **дату/время отчёта, тестируемый SHA**, окружение, шаги, фактическое/ожидаемое поведение, скриншоты/логи (если предоставлены).
- Чётко отделить **симптом**, **гипотезу** и **подтверждённую первопричину**. Указать, какая зависимость/подключение/обработчик/событие отсутствовали, если это доказано.
- В исправляющем коммите указать `Fixes: BUG-...`, какие строки/модули исправлены, почему это устраняет расхождение и что может сломаться.
- Записать повторный тест: тест разработчика отдельно от пользовательского. **До ответа тестера статус «ожидает пользовательской проверки», а не «исправлено и подтверждено».**
- Если отчёт не воспроизводится, не закрывать его без описания попыток, окружения и необходимых данных.

## 3. Коммит и неизбежная проблема самоссылки SHA
**Git SHA собственного коммита нельзя вписать в файл внутри этого же коммита**: изменение CHANGELOG меняет хеш коммита. Поэтому правила таковы:
- В том **же** коммите обновить CHANGELOG, указав стабильный `KR-YYYYMMDD-NNN` в записи **и точно такой же ID в commit message**. Поле `Git SHA` писать `определяется по git log --grep KR-...` до создания коммита.
- В ответе пользователю после создания коммита **обязательно дать фактический полный SHA и ссылку**. Для последующего аудита по ID запись однозначно сопоставляется с SHA в Git-истории.
- При следующем изменении допустимо дополнить SHA предыдущей записи вместе с CHANGELOG следующего коммита; **не создавать пустые вспомогательные коммиты только ради проставления текущего SHA**. Для уже известных SHA использовать точные значения.
- Проверить, что в каждом новом коммите есть изменение `CHANGELOG.md`. Исключение только для технически первого коммита при полностью пустом репозитории — его документировать **в следующем коммите**.
- `git log` является источником правды для коммит-хеша и точного времени Git; не придумывать SHA/точность до выполнения операции.

## 4. Шаблон записи
```markdown
## KR-YYYYMMDD-NNN — краткое название
- Дата/время: YYYY-MM-DDTHH:mm:ssZ (UTC)
- Коммит: <полный SHA или «см. git log --grep KR-...»>
- Этап / версия: ...
- Тип: feature | fix | refactor | docs | test | revert
- Задача/отчёт: Issue #... / BUG-... / запрос пользователя
- Изменённые файлы: ...

### Контекст и воспроизведение
Ожидалось: ...
Фактически: ...
Как воспроизвести: ...
Среда: ...

### Анализ причины
Наблюдения: ...
Гипотеза: ...
Подтверждённая причина: ... / НЕ УСТАНОВЛЕНА

### Что изменено и почему
- Файл/функция: старое -> новое; обоснование.
- Риски и совместимость: ...

### Проверки
- [PASS/FAIL/NOT RUN] тест, среда, подтверждение.
- Отдельно результат пользовательского теста (если есть).

### Выдано тестировщику
Коммит/PR/архив: ...
Шаги установки и тестирования: ...
Ожидаемое поведение: ...

### Фактический результат и следующие действия
Получено: ...
Не проверено: ...
Статус: требует тестирования | подтверждено | заблокировано
Связи: ...
```

## 5. Правило перед публикацией каждого коммита
1. Сначала прочитать последнюю запись CHANGELOG и состояние Issues/PR.
2. Подготовить и проверить изменения.
3. Добавить запись по шаблону **до коммита**; не писать успех без теста.
4. Убедиться, что `CHANGELOG.md` включён в тот же коммит и ID встречается в commit message.
5. Сверить diff и реальные проверки.
6. После коммита сообщить SHA, дату и время Git, ссылки, изменённые файлы, тесты и инструкцию пользователю.
7. Любая новая найденная ошибка — новый отчёт/запись; не стирать историю и не переписывать предыдущие наблюдения задним числом.

## 6. Нельзя
- Заменять подробный лог фразой «исправлены баги».
- Заявлять тест на Forever, если игру не запускали.
- Заявлять «причина найдена», когда есть только гипотеза.
- Скрывать регрессии/незакрытые баги.
- Делать кодовый коммит без CHANGELOG или с ID, не совпадающим с commit message.
