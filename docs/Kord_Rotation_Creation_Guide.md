## 0. Непреложные правила

1. **Одна архитектура:** `RotationEngine → ClassCommon → SpecCore (когда требуется) → Profile`. Это разделение ответственности, а не требование создавать лишний файл для каждого спека.
2. **Один контракт GameData:** одно каноническое имя, значение, тип и семантика для каждого сигнала. `moving` и `isMoving` не должны одновременно быть независимыми полями контракта; совместимость старых имён — только в одном адаптере.
3. **Никаких копий общей логики:** прежде чем добавлять функцию, искать аналог в Engine, GameData, ClassCommon и SpecCore. Общая логика принадлежит наиболее общему подходящему слою.
4. **Ротация — чистая функция:** `Next(state, options) → action | nil`; не вызывает WoW API, не кастует, не меняет `state`, `options` и общие таблицы.
5. **Неизвестное не равно разрешённому:** `nil` не подтверждает безопасность, доступность или возможность каста. Допустимый fallback документируется по каждому сигналу.
6. **Решения объяснимы:** действие содержит канонические поля идентификатора способности/команды, `phase`, `reason` согласно утверждённому контракту движка.
7. **Не объявлять готовым непроверенное:** синтаксис, модульные тесты, интеграция и проверка в клиенте — разные статусы.
8. **Источники обязательны:** референсные аддоны, сайты, серверные материалы и игровой клиент исследуются до реализации. Непроверенный источник нельзя выдавать за подтверждение.
9. **Самостоятельная реализация:** изучение референсов допускается для выявления поведения и подходов; код и структура Kord разрабатываются самостоятельно, без механического переноса чужого исходного текста.
10. **Сначала существующий репозиторий:** перед изменением прочитать актуальные `AGENTS.md`, инструкции проекта, интерфейсы Engine/GameData/Eligibility/BindingResolver и текущие профили. Документ не подменяет фактический контракт кода.

# Часть I. Исследование игровых механик

## Шаг 1. Зафиксировать рамки профиля

До написания кода записать: класс, специализацию, уровни (в частности Leveling и 60, если они отличаются), роль, контент (открытый мир/соло, подземелье, рейд, PvP), версию клиента и сервера, особенности талантов и рун, целевую экипировку, тип рекомендуемых действий. Указать, как определяется контекст (например, соло против группы), и что делать, если он неизвестен.

**Результат:** мини-спецификация, `id`, `version`, границы уровней, режимы и список ещё не проверенных предположений. Новые классовые профили не создавать без согласованного объёма работ.

## Шаг 2. Обязательное исследование источников — внутри этого гайда

Исследование **не пропускается** даже при наличии готовой ротации-референса. Сначала изучить материалы, затем зафиксировать факты и расхождения. Наличие сайта в списке не означает, что на нём гарантированно есть актуальная информация о WoW Forever: проверять применимость к версии и явно фиксировать «нет данных».

### 2.1. Первичные источники — максимальный приоритет при подтверждении механик

1. **Игровой клиент WoW Forever:** книга заклинаний, таланты, руны, ранги, тултипы, боевые события, наблюдаемая доступность способностей, реальные ограничения, тесты на манекене и мобах. Использовать только API-команды, действительно существующие в текущем клиенте; не предполагать наличие современных `C_Spell`-методов.
2. **Официальные материалы WoW Forever:** сайт, патчноуты, анонсы изменений, описание кастомных механик, официальные каналы и разъяснения разработчиков сервера.
3. **ForeverDB / база WoW Forever:** ID, ранги, эффекты, уровни, таланты, руны и изменения — при наличии соответствующих записей и подтверждении актуальности.
4. **Фактические данные боя:** игровые логи, combat log, проверенные записи боёв, повторяемые эксперименты. Отдельно фиксировать условия: версия, таланты, экипировка, длительность, тип цели.

### 2.2. Обязательные внешние информационные ресурсы

Для каждого профиля проверять релевантные материалы, фиксировать ссылку, дату, версию и применимость:

- **WoW Sims** — модели, симуляции, приоритеты и допущения; не переносить механики иной версии без проверки.
- **Warcraft Tavern(s)** — гайды, таланты, прокачка, PvE-приоритеты, полезные игровые сценарии.
- **Icy Veins** — приоритеты, cooldown management, специфика контента; проверять соответствие эпохе и серверу.
- **Wowhead** — заклинания, таланты, ранги, механики, комментарии; отдельно проверять версию базы.
- **ForeverDB** — серверные данные и кастомные элементы, если доступны.
- **Warcraft Logs и доступные аналоги** — наблюдаемое поведение игроков, но не автоматическое доказательство оптимальности.
- **Форумы, Discord, сообщества WoW Forever** — гипотезы, разборы спорных механик, сведения о недокументированных изменениях; обязательно перепроверять.

# Часть II. Архитектура и контракты

## Шаг 4. Проверить существующую архитектуру перед реализацией

Открыть актуальные файлы `RotationEngine`, `RotationProfiles`, `AbilityEligibility`, `BindingResolver`, GameData/адаптеры, TOC, UI и текущие профили нужного класса. Составить схему потока:

`WoW API → сбор/нормализация GameData → RotationEngine/выбор профиля → Next(state, options) → AbilityEligibility/проверка результата → BindingResolver/UI → рекомендация игроку`.

Порядок этапов в этой схеме **проверить по фактическому коду**; если реальный контракт отличается, документировать его до изменений. Ротация не выполняет нажатий и не обходит Eligibility или BindingResolver.

**Результат:** карта интерфейсов, список существующих помощников и точек интеграции, список изменений контракта (если необходимы).

## Шаг 5. Зафиксировать единый GameData

Каждый сигнал имеет каноническое имя, тип, смысл, источник, допустимые значения, семантику `true/false/nil`, частоту обновления и потребителей. Сигналы группируются по игроку, цели, заклинаниям, ресурсу, бою/угрозе, движению/касту, окружению/AoE, питомцу, талантам/рунам, автоатаке и режиму контента.

- **Один сигнал — одно имя.** Алиасы вроде `isMoving → moving` допустимы только в единой точке нормализации, если реально нужны для совместимости. Внутри профилей — только канонические имена.
- **`known`, `ready`, `usable`, `inRange`, `procActive` не смешивать.** Их фактические определения согласовать с AbilityEligibility. Не объявлять `ready` достаточным для действия, если движок требует отдельные условия.
- **Неизвестность:** опасные действия (например, AoE рядом с контролем) запрещены без подтверждения безопасности; безопасные fallback-решения разрешать только по явной политике.
- **Изменение контракта:** добавить/изменить поле в реестре, адаптере, тестах и потребителях; при несовместимом изменении предусмотреть миграцию или версионирование.
- **Не мутировать вход:** `Next` не изменяет переданные таблицы. Нормализация, если нужна, проводится в одном месте; не копировать всё состояние в каждом профиле без причины.

Пример таблицы:

| Сигнал | Тип | `true`/значение | `false` | `nil` | Поставщик |
|---|---|---|---|---|---|
| `moving` | boolean? | игрок движется | стоит | неизвестно, нельзя считать стоящим | GameData adapter |
| `playerLevel` | number? | уровень | неприменимо | уровень неизвестен | GameData adapter |

## Шаг 6. Разделить ClassCommon, SpecCore и Profile

```text
RotationEngine
  └── GameData / AbilityEligibility / BindingResolver
       └── <Class>_Common.lua          — общие проверки и политика класса
            ├── <Class>_<Spec>_Core.lua — повторяющиеся приоритеты специализации
            │    ├── <Class>_<Spec>_Leveling_PVE.lua
            │    └── <Class>_<Spec>_60_PVE.lua
            └── профили без отдельного SpecCore, если общая логика мала
```

Это **схема ответственности**, а не буквальная последовательность вызовов всех компонентов. Фактический порядок определяется движком.

- **Engine:** выбор профиля, жизненный цикл, общий контракт рекомендации.
- **GameData/Eligibility/BindingResolver:** сбор состояния, проверка применимости и связь с доступным действием/кнопкой.
- **ClassCommon:** общий контракт класса, помощники, единые политики питомца, выживания и поддержки, если они действительно общие.
- **SpecCore:** общая для Leveling/60 логика специализации и её приоритеты. Создавать, когда устраняет реальное дублирование; не выносить в него механики другого спека.
- **Profile:** только различия режима, уровней, доступности, настроек и вызов общей логики.

**Пример Hunter:** BM Leveling и BM 60 используют `Hunter_Common + Hunter_BM_Core`; SV Leveling и SV 60 — `Hunter_Common + Hunter_SV_Core`; MM может использовать `Hunter_Common` и собственную логику, пока отдельный MM Core не нужен. **BM не должен использовать SV Core** лишь ради формального единообразия.

Перед созданием новой функции провести поиск по Engine → ClassCommon → SpecCore → профилям. Если функциональность уже есть, переиспользовать. Изменения общих модулей требуют регрессионных тестов всех зависимых профилей.

## Шаг 7. Спроектировать приоритеты слоями

Сначала написать правила словами: входное условие, действие, причина места в приоритете, необходимые сигналы. Затем реализовать первое подходящее безопасное правило. Рекомендуемые слои, корректируемые под класс и контент:

1. Проверка состояния и допустимости цели.
2. Контекстная защита и выживание (например, сброс угрозы в группе не равен сбросу угрозы на обычном соло-мобе).
3. Поддержка питомца, аспектов/аур и подготовка.
4. Краткоживущие реактивные окна.
5. Крупные кулдауны с проверкой целесообразности.
6. Дебаффы/DoT с учётом TTD и ресурса.
7. AoE при подтверждённой безопасности и количестве целей.
8. Основной урон/лечение и filler.
9. Автоатака и служебные команды, если они не должны стоять раньше.

Не считать порядок универсальным: у конкретной специализации автоатака, реактивка или защита может требовать иной позиции. Все исключения обосновывать и тестировать. Разделять PvE-сценарии соло, dungeon и raid там, где меняются правила.

## Шаг 8. Настройки CFG: только обоснованные варианты поведения

**Настройка требуется, когда существуют несколько подтверждённых и разумных стратегий**, зависящих от контента или предпочтений. Неверный spellID, неверный кулдаун и неподтверждённая механика — не пользовательские настройки.

Каждая запись схемы имеет ключ, тип (`bool`, `enum`, `number`), безопасный default, допустимые значения/границы, описание, локализуемую подсказку, потребителя в коде и основание выбора. Числовые пороги, меняющие стратегию, настраиваемы; технические константы можно оставить в коде с объяснением. Не создавать настройку без читающего её правила; не дублировать общую настройку в нескольких профилях.

```lua
{ key = "mark", type = "enum", default = "smart",
  values = { "smart", "all", "elite", "boss", "off" },
  group = "debuffs", label = "Hunter's Mark",
  desc = "Стратегия применения метки; smart использует подтверждённые условия" }
```

Пример иллюстрирует **форму**, а не подтверждает игровую целесообразность каждого режима. Проверить соответствие существующей UI-схеме и шести языкам локализации. Неверные сохранённые значения валидировать централизованно; таблицы конфигурации не разделять по изменяемой ссылке между профилями.

## Шаг 9. Контракт действия и регистрация

`Next(state, options)` возвращает `nil` либо структуру, **строго соответствующую фактическому интерфейсу RotationEngine**. Если утверждённый контракт использует `spellID`, `spell`, `phase`, `reason`, вернуть именно их; для команды — согласованный отдельный тип. Не вводить новое поле действия без согласования с Engine, Eligibility, BindingResolver и UI.

Проверить регистрацию, выбор по классу/спеку/уровню/режиму, наличие способности и соответствие spellID/ранга, разрешение привязки, отображение `reason`, порядок загрузки TOC (общие файлы до зависимых профилей) и корректное поведение при отсутствии бинда или данных.

# Часть III. Реализация без дублирования

## Шаг 10. Порядок внесения изменений

1. Прочитать актуальные файлы и инструкции репозитория; зафиксировать базовую ревизию.
2. Составить таблицу: **новое правило → существующий помощник → место реализации → тест**.
3. Сначала обновить общий контракт/адаптер, только если это действительно необходимо.
4. Добавить или расширить ClassCommon и SpecCore, не ломая существующих потребителей.
5. Сделать тонкие Leveling/60-профили с минимальными различиями.
6. Обновить регистрацию и TOC, проверить, что профили реально загружаются.
7. Прогнать тесты всех зависимых профилей, а не только нового.
8. Подготовить отчёт: какие файлы изменены, какие проверки реально выполнены, что осталось непроверенным.

**Запрещено:** копировать одинаковые предикаты по профилям, вводить новые имена уже существующих сигналов, дублировать spellID без причины, скрыто менять общие таблицы, выдавать загрузку Lua за доказательство правильной ротации.

# Часть IV. Проверка, выпуск и сопровождение

## Шаг 11. Проверки по уровням доказанности

### 11.1. Статическая проверка

- Синтаксис совместим с **фактической Lua-версией клиента**; не использовать неподдерживаемые конструкции.
- Все зависимости существуют; TOC и регистрация согласованы.
- Нет повторных имён полей, неизвестных сигналов, неиспользуемых CFG, копий общей логики, мутирования входа.
- SpellID и API имеют подтверждение или явно помечены как неподтверждённые.

### 11.2. Модульные и сценарные тесты

Для каждого профиля тестировать: начало боя, нет цели, мёртвая цель, неизвестное движение, melee/ranged/мёртвая зона, недостаток ресурса, проки, питомца, угрозу, защиту, AoE с CC, TTD, отсутствие бинда, неверный CFG, уровни на границе и неизвестные сигналы. Для каждого теста указать **ожидаемое действие и причину**. Не считать примеры ниже универсальными приоритетами.

| Сценарий | Проверка |
|---|---|
| `moving=nil` | Не рекомендовать каст, требующий подтверждённой неподвижности |
| `breakableCCNearby=true` | Не рекомендовать опасный AoE |
| `playerLevel=59/60` | Выбран корректный профиль и допустимый набор способностей |
| Низкое HP + агро | Проверить защиту с учётом solo/dungeon/raid |
| Неизвестный `ready` | Не считать способность гарантированно доступной |
| Неверное значение CFG | Валидируется по схеме, не приводит к падению |

### 11.3. Интеграционные и регрессионные тесты

- Все профили загружаются в правильном порядке **через реальный загрузчик**, а не только через `loadfile`.
- `Next` получает канонические GameData и возвращает допустимое действие.
- AbilityEligibility корректно проверяет рекомендацию, BindingResolver разрешает её в интерфейсе, UI показывает действие и `reason`.
- Изменение Common проверяется на всех спеках класса; изменение GameData/Engine — на всех зарегистрированных профилях.
- Проверить, что Leveling и 60 не изменяют друг другу настройки или таблицы.
- Проверить отсутствие лишних аллокаций/дорогих операций в частом цикле обновления; оптимизировать только по измерениям.

### 11.4. Проверка в WoW Forever

Тестировать на манекене, одиночных мобах, в подземелье и рейде — **только в реально доступных режимах**. Проверить смену талантов/рун, питомца, движение, дальность, threat, защиту, длительные и короткие бои. Сравнивать рекомендации и логи с подтверждёнными механиками, аптаймами, простоями, расходом ресурса и результатом боя. Фиксировать дату, версию и условия.

**Статусы строго различать:** `Исследовано` → `Реализовано` → `Статически проверено` → `Модульно проверено` → `Интегрировано` → `Проверено в игре`. Последний статус запрещён без реального игрового теста.

## Шаг 13. Сопровождение

Изменение патча, клиента или референсов → обновить реестр фактов → оценить затронутые сигналы и модули → исправить код → прогнать регрессию всех зависимых профилей → при возможности проверить в игре. Каждую воспроизведённую ошибку закреплять отдельным тестом. Изменение поведения профиля отражать в его версии и журнале изменений; не требовать самостоятельной версии каждого вспомогательного файла без необходимости.
