# Profile Contract v1 — профиль ротации и граница с ядром

**Статус:** канонический проект v1 после ревью 2026-11-21. Не реализован. Игровой клиент WoW Forever не проверялся: всё, что относится к его API, остаётся гипотезой до дампа DevTools.

## 1. Цель и границы

Профиль содержит логику приоритетов спека. Ядро (`GameState`, `AbilityEligibility`, `RotationEngine`) отвечает за данные, проверку способностей и правило остановки. Профиль не обращается к игровому API и не подтверждает готовность способности.

Не добавляем: второй механизм доступности способностей, полный снимок всех данных на каждом проходе, постоянное сканирование аур и врагов, диагностическую запись и изменённое поведение ядра в пользовательской сборке. `KordRotation` остаётся побайтово одинаковым в пользовательской и диагностической поставках.

## 2. Структура профиля

```lua
Profile = {
  contractVersion = 1,
  id = "HUNTER_BM_LEVELING_PVE", version = "x.y.z",
  classToken = "HUNTER", specIndex = 1, levelMin = 1, levelMax = 59,
  status = "draft",                  -- draft | mock_tested | experimental | verified (раздел 9)
  Spells = { Name = spellID, ... },  -- полный набор допустимых spellID
  Needs = {                          -- разрешённые источники, не предзагрузка
    auras = { <spellID>, ... },
    ranges = { <spellID>, ... },
    enemyCount = false, ttd = false, swing = false,
  },
  Config = { ...схема CFG... },      -- раздел 6
  Rules  = { ...упорядоченные правила... },  -- раздел 3
}
```

Реестр отклоняет профиль при несовпадении `contractVersion`, неизвестных ключах `Needs`, spellID вне `Spells`, дубликатах и неверных типах.

## 3. Правило и условия

```lua
{ spell = "SerpentSting", type = "SPELL",
  when = S.all(
    function() return S:isNot("target.debuff", 1978) end,
    function() return S:ge("target.ttd", cfg.stingMinTTD) end),
  onUnknown = "stop",     -- "stop" (по умолчанию) | "skip" (раздел 5)
  reason = "Maintain Sting" }
```

**`S` состоит только из методов.** Сырой снимок спрятан в замыкании, прямого чтения полей нет по построению. Это и есть защита от `if state.aura then`; прокси в ядре не нужен.

**Составные условия ленивые.** `all` и `any` принимают функции, а не готовые значения, и вычисляют их по порядку:

| Оператор | Поведение |
|---|---|
| `all` | первое `false` → `false`; первое `nil` → `nil` (останавливается, дальше не читает); иначе `true` |
| `any` | первое `true` → `true`; `nil` запоминается, чтение продолжается в поисках `true`; без `true` → `nil`, если был `nil`, иначе `false` |

Простые проверки: `is`, `isNot`, `eq`, `ge`, `le`. Каждая возвращает `true`, `false` или `nil`.

## 4. Запросы о способностях

Единственный источник — `AbilityEligibility`; результат кэшируется на одну оценку. Профиль запрашивает одно из двух:

- `S:spellAvailable(id)` — окончательная доступность способности: `READY`, `BLOCKED` или `UNKNOWN`.
- `S:spellFact(id, kind)` — подтверждённый факт: `known`, `cooldownActive`, `inRange`, `chargesAtLeast`. Результат `true`, `false` или `nil`. Общий кулдаун и GCD различаются источником; если источник не подтверждён, ответ `nil`.

Условие профиля `true` не означает готовности способности: итог выдаёт только `AbilityEligibility` (раздел 5).

## 5. Алгоритм и политика UNKNOWN

Для каждого правила по порядку:

1. Вычислить `when` под `pcall`. Исключение = `UNKNOWN`, причина `condition_error`, всегда `stop`.
2. `false` → следующее правило.
3. `nil` → `stop`: вернуть `UNKNOWN` с причиной; `skip`: следующее правило, причина идёт в диагностику.
4. `true` → если `type` не поддерживается, пропустить правило с `unsupported_action`; иначе передать `spellID` в `AbilityEligibility`.
5. `READY` → одна рекомендация; `BLOCKED` → следующее правило; `UNKNOWN` → стоп.
6. Правила ниже подходящего не вычисляются. Если подходящих нет, результат `BLOCKED`, причина `no_eligible_rule`.

**`skip` допустим только** для сознательно разрешённого отказа от необязательного улучшения. **Запрещён** для: ошибок кода (`condition_error`), неизвестной готовности способности (`UNKNOWN` от Eligibility), защитных условий и дорогих способностей. Каждый `skip` — строка таблицы допустимых исключений (профиль, правило, условие, обоснование, ID теста); правило с `skip` вне таблицы реестр отклоняет.

## 6. Config (CFG)

Запись схемы: `{ key, type = "enum"|"bool"|"number", default, values|min|max, group, label, desc, conflict }`. Значение вне допустимого → дефолт. UI генерируется из схемы; `conflict` описывает расхождение источников.

## 7. Типы действий

| Тип | Статус |
|---|---|
| `SPELL` | поддерживается по проверенному контракту |
| `PET_COMMAND` | не поддерживается: правило пропускается с `unsupported_action`, иконка не показывается |

Новые типы добавляются только вместе с контрактом безопасного отображения и тестами.

## 8. Данные и кэш

- Чтение по `Needs`, по необходимости, один раз за оценку.
- Ключ кэша: идентификатор оценки, имя запроса, параметры.
- Долгое кэширование — только с инвалидацией по ревизиям каналов EventBus.
- Провайдеры (ауры по spellID, дальность, число врагов, TTD, swing, максимальный изученный ранг) реализуются в ядре и подключаются после подтверждения в матрице v14.

## 9. Статусы профиля

Булев `verified` заменён четырьмя уровнями, которые не смешивают структуру, тесты и игровое подтверждение:

| `status` | Что подтверждено | Где допустим |
|---|---|---|
| `draft` | структура принята реестром | только в тестах |
| `mock_tested` | пройдены mock-тесты раздела 11 | тесты, DevTools |
| `experimental` | запущен в игре без подтверждения | только при явной настройке `allowUnverifiedProfiles` (по умолчанию выключена) |
| `verified` | подтверждён в WoW Forever | обычная пользовательская ротация |

Допуск определяется данными профиля и настройкой, а не отдельной веткой кода ядра.

## 10. Проверки

- `pcall` вокруг каждого вызова профиля; валидация результата (spellID из `Spells`, статус из списка).
- Статическая проверка: профиль не обращается к игровым глобальным функциям. Она выполняется тестовым помощником вне ядра.
- Бюджет времени оценки определяется замерами DevTools на клиенте, без заранее заданного лимита.
- GitHub Actions запускаются вручную перед общим QA; локальный прогон тестов обязателен.

## 11. Тесты (mock)

1. Неизвестный верхний приоритет блокирует нижний, если не разрешён `skip`.
2. `skip` пропускает правило и пишет причину; вне таблицы исключений он отклоняется.
3. Ошибка в `when` даёт `stop`, даже при `skip`.
4. Ленивость: правила ниже подходящего и аргументы `all`/`any` после решающего не вычисляются.
5. `BLOCKED` от Eligibility ведёт к следующему правилу, `UNKNOWN` — к остановке, `skip` для него запрещён.
6. Неподдерживаемый тип пропускается с `unsupported_action` и не отображается.
7. В `S` нет прямых полей снимка.
8. Невалидный профиль (версия контракта, spellID вне набора, `skip` вне таблицы, неизвестный `status`) отклоняется.
9. Различие `spellAvailable` и `spellFact`; общий кулдаун без подтверждённого источника даёт `nil`.
10. Дифференциальный тест BM: одинаковые состояния, расхождения старой логики (`nil` = ложь) и новой документируются.
