# ROADMAP — этапы разработки Kord Rotation

**Режим разработки:** выполнять все подшаги одного этапа последовательно, коммит + подробный CHANGELOG после каждого; просить **один общий игровой тест только после полной сборки этапа**, затем разбирать весь список ошибок. Источник правды для этапа 1: **[STAGE_01_INTERFACE.md](STAGE_01_INTERFACE.md)**. Статусы: PLANNED / IN PROGRESS / BLOCKED / DONE только по фактическим результатам и тестам.

## Этап 1 — подробно
Реализовать `0.1.0`–`0.1.7`; **см. полный спецификационный документ** [STAGE_01_INTERFACE.md](STAGE_01_INTERFACE.md), разделы 1.0–1.18. В частности:
- Автодетектор класса, подсчёт очков 3 веток, ничьи и неизвестные значения;
- Боевая панель (3 иконки, от 1 до 5, перемещение, размеры, видимость, текст, эффекты);
- Девять вкладок и содержание каждого поля;
- Структура файлов, SavedVariables и разграничение логики UI;
- Диагностика и реальные тесты Forever;
- Критерии готовности. **Нельзя заменять ссылку коротким пунктом и считать ТЗ первого этапа выполненным.**

**После 0.1.7:** не переходить к этапу 2 и не просить пользовательский QA немедленно: пройти `docs/STAGE_01_COMPLETION_AUDIT.md`, закрыть оставшиеся элементы §1.0–1.18, затем выдать единый кандидат и `docs/STAGE_01_QA_PLAN.md`. Статус этапа 1 остаётся IN PROGRESS, пока нет полного кода и игрового подтверждения.

## Этап 2 — ядро игровых данных
- Проверить API по каждому типу данных в бою и вне боя; таблица возможностей по конкретной версии клиента.
- Нормализовать игрока, цель, бой, доступные заклинания, ранги, кулдауны, касты, ресурсы и ауры — только где API позволяет.
- Событийная модель + throttling + защита от ошибок, запись ограничений в диагностику.
- Критерий: стабильно работающий адаптер и тесты на манекене/в бою, без ложного чтения секретных данных.

## Этап 3 — первая полноценная ротация
- Пилот: Воин «Оружие» (если есть тестовый персонаж и необходимые данные; иначе выбрать реально проверяемую ветку).
- Реализовать список способностей и приоритеты, ST/AoE/manual fallback, обработку недоступных условий.
- Отображать 1–3 шага лишь когда движок может обосновать каждый шаг.
- Критерий: записанные сценарии, тесты пользователя, причины выбора и выявленные ограничения.

## Этап 4 — система ротационных профилей
- Формат профиля `CLASS/TREE`, ID правил, категория, условие, приоритет, enable/disable, version.
- Система переопределений, наборы дефолтных значений, миграции и валидатор.
- Критерий: добавление нового профиля не требует переписывания Core и UI.

## Этап 5 — покрытие 27 веток
- По одному и затем по три профиля каждого класса; индивидуальная проверка с живым персонажем.
- DPS: урон/ST/AoE, танки: защита/угрозы/возможные сейвы, хилы: лечебные приоритеты с учётом доступного API.
- Поддержка талантов и отличающихся билдов; матрица тестирования.
- Критерий: все 27 профилей имеют явный статус реализован/ограничен/не проверен, а не номинальную заглушку.

## Этап 6 — качество
- Профилирование производительности, борьба с утечками/дублирующими событиями, журналы выбора и диагностика.
- Регрессия после каждого изменения, подтверждение тестером и воспроизводимые отчёты.
- Критерий: стабильность в реальном геймплее на зафиксированной версии клиента.

## Этап 7 — релиз
- Проверить `.toc` и `Interface`, сборку папки/ZIP, установку с нуля, локализации, лицензии.
- Версионирование, пользовательская инструкция, CHANGELOG и известные ограничения.
- Критерий: чистый ZIP, проведённая регрессия и документированный релиз.

## Управление этапами
Внутри этапа не требовать от пользователя устанавливать каждую промежуточную сборку. После всех подшагов представить один полный тест-план; перед присвоением этапу статуса DONE требуется результат комплексного теста и запись в CHANGELOG. Если тест недоступен, писать «не проведён», а не «успешно». Пересмотр плана — отдельное изменение с причиной и ссылкой на коммит/Issue.
