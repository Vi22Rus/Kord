Источник правды для этапа 1: **[STAGE_01_INTERFACE.md](STAGE_01_INTERFACE.md)**. Статусы: PLANNED / IN PROGRESS / BLOCKED / DONE только по фактическим результатам и тестам.

## Этап 2 — ядро игровых данных: подробный план (PLANNED)

**Цель:** построить проверяемое, устойчивое к отсутствующим API ядро получения состояния игры и выдачи **данных** о допустимых рекомендациях. Этап 2 НЕ означает готовую боевую ротацию: первое содержательное правило приоритетов и живой ротационный профиль относятся к этапу 3.

**Обязательные принципы:**
- Только штатный публичный API WoW Forever с проверкой существования, типа возвращаемых значений и фактического поведения; ни секретные/защищённые данные, ни защищённые действия не обходить.
- Никаких автоматических нажатий, передачи команд в Windows, RGB-сигналов, специальных пиксельных индикаторов, скрытого экспорта рекомендаций или доступа к внешним программам. Аддон показывает рекомендации игроку.
- **Жёсткий допуск:** способность-кандидат должна быть подтверждена на разрешённой панели действий Blizzard. Наличие в книге заклинаний само по себе недостаточно. Неизвестное состояние => не рекомендовать (fail closed).
- Система рекомендаций пропускает отсутствующую на панели, неподтверждённую либо непригодную способность и рассматривает следующего кандидата по приоритету. Если допустимых нет, возвращает пустой результат, а не тестовую заглушку. При нескольких слотах одного заклинания — детерминированный выбор.
- Привязки клавиш определяются через реальные API биндов и слотов. При отсутствии привязки показывается рекомендация без подписи клавиши **только если** слот достоверно существует; отсутствие клавиши не означает отсутствие способности.
- Внутренние ID/коды не должны разрушать отображение нормальных иконок, локализацию, поддержку рангов и возможность диагностики. Маскировку ID считать только повышением порога анализа, а не антибот-защитой.
- Сохранить текущие интерфейс, девять вкладок, параметры и профили; новые UI-строки и уникальные подсказки — на шести языках; без ложных утверждений о проверке в клиенте.

### 2.1. Инвентаризация клиента, референсов и API-контрактов — RESEARCH COMPLETE / GAME QA NOT RUN
- Изучить текущее `SpellCatalogue`, `RotationSettings`, `SafeActions`, `SpecDetector`, `RotationDisplay`, `SpellIcon` и .toc; сопоставить возможности из доступных Sonah, JustAC, MaxDps, ForeverRotation, ForeverAuras, RotationGuide с их лицензиями.
- Составить матрицу API/событий Forever: книга заклинаний, слот/тип действия, ID/ранг, макросы, бинды, класс/таланты, цель, бой, касты, КД, ресурсы, ауры. Для каждой записи: используемый API, наличие, надёжность, возможные альтернативы, UNKNOWN при отсутствии данных.
- Закрепить схемы данных и запрет на подмену реальных значений тестовыми.
**Результат:** [STAGE_02_01_API_RESEARCH.md](STAGE_02_01_API_RESEARCH.md) — матрица, контракты, исследование шести ZIP и выявленные дефекты загрузки; игровое подтверждение NOT RUN.

### 2.2. Безопасный слой вызовов и сбор событий
- Создать/расширить единую обёртку API с `pcall`, проверкой результатов и явными статусами READY/UNKNOWN/UNAVAILABLE/ERROR.
- Организовать подписку на штатные события с редким резервным обновлением и ограничением частоты; исключить лишние дубли и обработчики, падающие при отсутствии API.
- Разделить вычисление состояния игры, диагностику и отображение.
**Готово, когда:** отсутствие одного API не ломает панель и не превращается в ложное «способность доступна».

### 2.3. Снимок состояния игрока, цели и боя
- Нормализовать GUID/существование и отношение к цели, дальность только при доступном API, смерть, бой, транспорт/верховую езду, каст/канал, ресурсы, глобальную и локальные задержки там, где достоверны.
- Определить срок актуальности снимков и правила инвалидирования по событиям.
**Готово, когда:** каждый параметр имеет тип, источник, время чтения и честное UNKNOWN вместо угаданного значения.

### 2.4. Каталог способностей, ранги и переобучение
- На основе текущего `SpellCatalogue` читать реальные изученные способности, ранги и их ID; не заводить искусственную полную таблицу всех заклинаний игры.
- Корректно обновлять каталог при смене талантов, обучении/смене ранга, смене персонажа; для неоднозначного ID/имени не угадывать.
- Развести стабильный технический идентификатор и локализованное имя/иконку.
**Готово, когда:** обновление книги не создаёт дубликаты или несуществующие известные способности.

### 2.5. Сканер штатных панелей Blizzard
- Проверить фактические диапазоны слотов, страницы основных/дополнительных панелей, режимы и формы/стойки клиента Forever; не считать заранее, что доступен каждый современный API.
- Сканировать `HasAction`/`GetActionInfo` и аналоги лишь при их наличии; учитывать прямые способности, доступные варианты рангов, доступные action-слоты и переходы страниц.
- Макросы, предметы, питомцы и действия нестандартных панелей считать отдельно; допускать к ротации лишь при **однозначно подтверждённой** связи с конкретной способностью и поддерживаемом контракте. Не выполнять/не разбирать небезопасно произвольный макрокод.
**Готово, когда:** выдаётся подтверждённое соответствие «способность ↔ слот(ы)» или UNKNOWN; вне разрешённой панели способность не проходит фильтр.

### 2.6. Реальные бинды и надписи сочетаний клавиш
- Сопоставить action-слот с командами Blizzard и `GetBindingKey`/поддерживаемыми API; учитывать две клавиши, модификаторы Shift/Ctrl/Alt, назначенные страницы, перестановки и изменения биндов.
- Отличать незабинденный слот от отсутствующего слота; при нескольких допустимых слотах применять задокументированный приоритет выбора и краткую читаемую подпись.
- Не выдавать `keyLabel` из существующих настроек за обнаруженный игровой бинд: решить миграцию/ручной fallback отдельно, без ложной маркировки «авто».
**Готово, когда:** UI получает реальный `bindingLabel` и его источник; в тестах изменения назначения и удаления клавиши не оставляют устаревших подписей.

### 2.7. Доступность способностей в текущем состоянии
- Для изученных и расположенных на панели способностей читать фактические КД, ресурс/стоимость, применимость к цели, каст и доступность действия при наличии API.
- Разделять READY, BLOCKED и UNKNOWN; неизвестное критическое условие не считать выполненным.
- Содержать причины отклонения в диагностике, не маскируя их под рабочую ротацию.
**Готово, когда:** адаптер никогда не сообщает «можно применить» без необходимых подтверждений.

### 2.8. Контракт выбора кандидатов и пропуска
- Создать независимый от конкретного класса фильтр последовательности кандидатов, подготовленный для этапа 3; на этапе 2 использовать только контролируемые сценарии/фикстуры, не объявляя их боевой ротацией.
- Алгоритм: по приоритету проверить разрешённую панель → актуальность слота → условия/категории/ресурс/КД → добавить рекомендацию; иначе перейти к следующему. При отсутствии кандидатов вернуть пустую очередь, очистить прежние слоты.
- Не допускать скрытого fallback на заклинание вне панели и не «перепрыгивать» через UNKNOWN с выдачей выдуманного состояния.
**Готово, когда:** тесты покрывают отсутствие первого/всех/дублированных/перемещённых заклинаний и смену страницы без ложных рекомендаций.

### 2.9. Вывод рекомендаций и привязок без тестовых заглушек
- Подключить структурированный результат к существующим `RotationDisplay` и `SpellIcon` без изменения стиля; показывать реальную иконку/клавишу только при подтверждённых данных.
- Развести тестовый режим интерфейса и будущий production-режим; пустой результат очищает и скрывает содержимое по настройкам, не оставляет предыдущую иконку.
- Сохранить адаптивность панели (1–5 слотов), позицию, размеры, визуальные эффекты, профили оформления.
**Готово, когда:** пользователь не может спутать тестовую иконку с реальной рекомендацией.

### 2.10. Усложнение подключения RGB/пиксельной авторотации
- Провести аудит всех видимых/экспортируемых путей: нет ли RGB-кодировщика, полосы данных, фиктивных цветовых сигналов, API для машинного чтения, логов/чат-сообщений с рекомендованными Spell ID и клавишами.
- Не добавлять машинно-читаемые коды, фиксированные цветовые маркеры, скрытые управляющие пиксели, внешние библиотеки передачи. Хранить технические ID только внутри логики и необходимых локальных настроек; не показывать ID в боевой панели.
- Оценить вариант внутренних кодов для таблицы способностей отдельно: без доказанной пользы не вводить массовую статическую замену Spell ID (клиент, исходники и пользовательские иконки остаются наблюдаемыми).
- Указать границу защиты: пользовательскую UI-рекомендацию теоретически можно распознать через изображение; из открытого Lua-аддона нельзя гарантированно скрыть семантику от стороннего кода.
**Готово, когда:** аудит подтверждает отсутствие специально организованного канала для автоматизации и документирует остаточные риски; обещания «невозможно сделать бота» отсутствуют.

### 2.11. Диагностика, локализация и устойчивость
- Добавить причины недоступности панели/биндов/API/состояния в диагностику с ограничением частоты; не выводить необработанные данные в общедоступный экран/чат как командный канал.
- Все новые видимые тексты и собственные подсказки перевести на ruRU/enUS/deDE/frFR/esES/ptBR, с предусмотренными алиасами.
- Проверить инвалидацию кэшей после логина, `/reload`, смены страницы, привязок, талантов, формы и боя; контролировать производительность.
**Готово, когда:** диагностика различает отсутствие данных, отсутствие бинда и отсутствие способности на панели; локали совпадают по ключам.

### 2.12. Общая статическая регрессия и единый игровой QA
- Проверить синтаксис Lua, порядок .toc, доступность модулей/методов, отсутствие выдуманных API, миграции и качество новых UI-строк.
- Подготовить единый чек-лист игровых случаев: 0/1/несколько слотов, ключи с модификаторами, пустая панель, неизвестное API, макрос, смена стойки/страницы, обучение, КД, ресурс, бой/вне боя, отсутствие следующей способности, отсутствие RGB-канала.
- Делать отдельный коммит и запись CHANGELOG на каждый завершённый подэтап; не просить установку между подэтапами. После 2.12 — одна сборка для теста пользователем; без результата из клиента статус `IMPLEMENTED / AWAITING IN-GAME QA`, не DONE.
**Готово, когда:** составлен воспроизводимый отчёт PASS/FAIL/NOT RUN, все ограничения перечислены, а игровое подтверждение не придумано.

**Зависимости:** 2.1 → 2.2 → (2.3 и 2.4) → 2.5 → 2.6 → 2.7 → 2.8 → 2.9 → 2.10 → 2.11 → 2.12. Подэтап 2.10 допускает параллельный аудит, но его результат должен быть учтён в 2.9. При обнаружении, что нужный API недоступен, регистрировать BLOCKED/ограниченный режим, а не обходить защиту клиента. ## Управление этапами
Внутри этапа не требовать от пользователя устанавливать каждую промежуточную сборку. После всех подшагов представить один полный тест-план; перед присвоением этапу статуса DONE требуется результат комплексного теста и запись в CHANGELOG. Если тест недоступен, писать «не проведён», а не «успешно». Пересмотр плана — отдельное изменение с причиной и ссылкой на коммит/Issue.
