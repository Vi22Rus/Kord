# Требования к движку Kord

Каждый пункт содержит требование, результаты проверки исходников, вердикт и конкретные действия. Документ не означает автоматического изменения кода движка.

## PR-PR-01 — Сквозная трёхзначная логика (true / false / nil)

**Область:** игрок, цель, ауры, предметы, условия, проверка пригодности способностей и приоритеты.

### Требование

| Значение | Семантика |
|---|---|
| `true` | Достоверно подтверждено |
| `false` | Достоверно опровергнуто |
| `nil` | Неизвестно / недоступно / небезопасно для чтения |

Не подменять `nil` значением `false` или `0`. Отсутствие прочитанного дебафа не означает доказанного отсутствия дебафа; неизвестное количество предметов не равно нулю. Семантика должна сохраняться от API и провайдеров до условий, приоритетов и окончательной проверки способности. Неизвестность в более высоком приоритете нельзя молча пропускать, если она может изменить выбор.

Ожидаемая трёхзначная логика: `false AND nil = false`, `true AND nil = nil`, `true OR nil = true`, `false OR nil = nil`, `NOT nil = nil`. Для `AND` нельзя возвращать `nil` до проверки оставшихся операндов на достоверный `false`.

### Фактическая реализация Kord (исходники GitHub, ветка main)

**Механизм присутствует, но не полностью корректен.** Проверены следующие места:

- [`KordRotation/Core/RotationConditions.lua`](KordRotation/Core/RotationConditions.lua), строки 193–255: `observe`, `is`, `isNot`, `eq`, `ge`, `le`, `all`, `any` возвращают булевы значения либо `nil` при неизвестности. `any` собирает признак неизвестности и продолжает проверять последующие операнды.
- **Подтверждённая ошибка:** `RotationConditions.lua`, строки 232–241, `methods:all(...)`: после первого `nil` сразу выполняется `return nil` (строка 239), хотя последующий операнд может вернуть `false`. Пример: `all(() => nil, () => false)` в терминах логики должен давать `false`, но текущий Lua-алгоритм вернёт `nil`. Исправление: запомнить наличие `nil`, продолжить вычисление до первого `false` либо конца списка, затем вернуть `nil`, если неизвестность была и `false` не найден.
- [`KordRotation/Core/RotationEngine.lua`](KordRotation/Core/RotationEngine.lua), строки 202–239: `false` превращается в `BLOCKED`, `nil` — в `UNKNOWN`, `true` передаёт управление в `AbilityEligibility` через `RotationConditions:Check`. При `UNKNOWN` приоритет обычно останавливается; исключение — `rule.onUnknown=="skip"` при `reason=="condition_unknown"` (строки 235–238). Политика `skip` требует отдельной проверки безопасности каждого правила.
- [`KordRotation/Core/GameState.lua`](KordRotation/Core/GameState.lua), строки 349–383: `player.travelAspect` возвращает достоверный `false` только если обе проверяемые ауры достоверно отсутствуют; иначе сохраняет `UNKNOWN` либо использует положительное подтверждение из `AuraEvidence`.
- `GameState.lua`, строки 503–599: для аур есть несколько проверок идентичности, защищённости, имени, режима секретности и запасного источника `AuraCooldownViewer`; невозможность чтения не должна означать отсутствие.
- [`KordRotation/Core/AbilityEligibility.lua`](KordRotation/Core/AbilityEligibility.lua): используется разделение `READY`, `BLOCKED`, `UNKNOWN`, включая неизвестные сведения о книге заклинаний и перезарядке.
- [`KordRotation/Core/GameAPI.lua`](KordRotation/Core/GameAPI.lua): присутствует безопасная оболочка чтения API и проверка защищённых значений.

**Граница проверки:** наличие перечисленных защит подтверждено просмотром файлов, но сквозное покрытие всех данных игрока, цели, предметов и всех профилей ещё не доказано. Это не отменяет установленную ошибку `all`.

### Референсы

- **Sonah** — ориентир для различения подтверждённого отсутствия ауры/предмета и неизвестного состояния. Для адресной проверки: `Sonah/Core/Atoms/Auras.lua` (`ReadApi`), `Sonah/Core/Atoms/Items.lua` (`Items.Count`).
- **Rotation Master** — ориентир для обработки нечитаемых значений и передачи неопределённости через условия. Для адресной проверки: `RotationMaster/Core/conditions.lua` (`switchUnitWitness`).
- **MaxDps** — встречаются `true`, `false`, `nil`, но нет подтверждения единой сквозной трёхзначной модели; не использовать как единственный образец. Для проверки: `MaxDps/Helper.lua`.

Примечание: референсные наблюдения основаны на предыдущем предварительном сравнении; в данном обновлении не выполнена новая построчная проверка архивов. Не выдавать их за доказанную полную реализацию.

### Вердикт

**РЕАЛИЗОВАНО — НЕОБХОДИМО ИСПРАВИТЬ.**

Основание: конкретный воспроизводимый по коду дефект `RotationConditions.methods:all`. Дополнительно нужен аудит покрытия источников данных и правил `onUnknown="skip"`.

### Требуемые действия при отдельной команде на изменение движка

1. Исправить `methods:all` в `KordRotation/Core/RotationConditions.lua` с сохранением ленивого вычисления и приоритетом достоверного `false` над ранее увиденным `nil`.
2. Добавить тесты комбинаций `true / false / nil` для `all`, `any`, `isNot`, включая порядок операндов.
3. Проверить чтение данных игрока, цели, аур и предметов на скрытое преобразование `nil` в `false` или `0`.
4. Проверить все применения `onUnknown="skip"` на риск выдачи ложной рекомендации.

**Код движка не изменён; исправлена только документация требований.**


## PR-02 — Проверка защищённых (secret) значений до сравнений и арифметики

### Требование

Любое значение, полученное от игрового API или из вложенного поля, должно быть проверено на секретность и доступность **до** сравнения, арифметики, логической проверки значения, конкатенации и использования как индекса, если операция может быть запрещена клиентом. Проверять `issecretvalue`, `issecrettable`, `canaccessvalue` там, где они доступны; ошибки проверок считать неопределённостью. Если значение защищено, логический результат — `nil` (UNKNOWN), а не `false`, `0` или угаданное значение. Внутренний контракт провайдера вправе представлять это как `{status="UNKNOWN",reason="protected_value"}`, но не должен выдавать READY/BLOCKED по непроверенному значению.

### Проверка Kord — исходники ветки main

- [`KordRotation/Core/GameAPI.lua`](KordRotation/Core/GameAPI.lua), строки 73–93: централизованный `secret(value)` проверяет `issecretvalue`, `issecrettable`, `canaccessvalue` через `pcall`; отказ и ошибка проверки трактуются как защищённость.
- `GameAPI.lua`, строки 114–135 (`Read`), 137–168 (`ReadTuple`), 171–191 (`ReadValues`): результаты API проверяются через `secret` перед сравнением чисел; защищённое значение даёт `UNKNOWN/protected_value`.
- `GameAPI.lua`, строки 194–221 (`ReadField`, `IsSafeValue`): контейнер и извлечённое поле проходят защитную проверку. Потребители могут использовать `IsSafeValue`.
- [`KordRotation/Core/RotationConditions.lua`](KordRotation/Core/RotationConditions.lua), строки 29–35 и 193–230: условия используют `GameAPI.IsSafeValue` и возвращают `nil` для недостоверных значений.
- [`KordRotation/Core/AbilityEligibility.lua`](KordRotation/Core/AbilityEligibility.lua): применяет `IsSafeValue` к данным и параметрам, использует `UNKNOWN` при отсутствии надёжных сведений.

**Подтверждённый дефект на границе безопасности:** `GameAPI.ReadField(record,key,expectedType)` проверяет тип `key` (строка 202) и затем использует `record[key]` (строка 205), **не проверяя сам `key` через `secret(key)` до индексации**. Секретный строковый/числовой ключ может дойти до запрещённой операции. `pcall` предотвращает необработанную ошибку, но не выполняет требование «проверить до операции». Требуется предварительная проверка `secret(key)` и возврат `UNKNOWN/protected_value`. Аналогично стоит отдельно проверить входные аргументы и метаданные контрактов `Read`/`ReadTuple`/`ReadValues` перед любым потенциально запрещённым использованием.

**Граница заключения:** просмотрены основные пути чтения и условий, но не доказано отсутствие прямых небезопасных операций во всех файлах интерфейса, профилей и DevTools.

### Сравнение с референсами (исходники архивов проекта)

- **Sonah**, `Sonah/Core/Atoms/Secret.lua`, строки 17–58: `Secret.Is` централизованно распознаёт секретные значения и таблицы; `Secret.Plain`, `Secret.Number`, `Secret.Bool` возвращают `nil` для секретных данных. **Основной образец для безопасного преобразования входных значений.**
- **Rotation Master**, `RotationMaster/Core/condition_support.lua`, строки 29–35 и 62–79: секретные источники трактуются как недоступные, пока не подтверждена читаемость; ограничения проверяются консервативно. **Образец политики UNKNOWN для условий.**
- **MaxDps**, `MaxDps/Core.lua`, строки 86–88: предоставляет `MaxDps:issecretvalue`; в `MaxDps/Helper.lua` есть точечные проверки перед использованием значений. **Образец отдельных защит, но не доказательство полной централизованной гарантии.**

### Вердикт

**РЕАЛИЗОВАНО — НЕОБХОДИМО ИСПРАВИТЬ.** Центральная защита есть и работает по принципу fail-closed, но обнаружен конкретный путь использования потенциально секретного ключа до проверки.

### Что исправить по отдельной команде

1. `GameAPI.ReadField`: проверить `secret(key)` **до** `record[key]`; возвращать UNKNOWN с причиной.
2. Проверить входные аргументы и метаданные методов `Read`, `ReadTuple`, `ReadValues` до индексирования/сравнений, сохранив fail-closed.
3. Добавить регрессионные тесты на secret-число, secret-boolean, secret-строку, secret-таблицу, secret-ключ и ошибки пробников.
4. Провести сквозной поиск прямых сравнений и арифметики с результатами WoW API вне `GameAPI`, включая профили и UI.

**Изменения движка:** не выполнялись; это только фиксация требования и аудита.


## PR-03 — Только чтение данных и рекомендации; без автоматического управления персонажем

### Требование

Движок получает игровые данные через разрешённые операции чтения, оценивает состояние и показывает рекомендацию. Он **не должен** самостоятельно нажимать кнопки или слоты панели, запускать макросы, применять заклинания/предметы, менять текущую цель, устанавливать назначения клавиш либо создавать обходной механизм защищённых действий. Пользователь сам совершает игровые действия. Допустимы обычные операции интерфейса аддона (отображение, настройки, обновление фреймов), если они не выполняют игровые действия за пользователя.

### Проверка реального исходного кода Kord

- [`KordRotation/Core/GameAPI.lua`](KordRotation/Core/GameAPI.lua), строки 2–7, 60–70, 114–191: явно объявлен **read-only allowlist**; вызовы игровых API идут через ограниченный `resolve` и читающие `Read`, `ReadTuple`, `ReadValues`. Исполняющие игровые действия API в этот разрешённый интерфейс не включены.
- [`KordRotation/Core/RotationEngine.lua`](KordRotation/Core/RotationEngine.lua), строки 202–253: условия и `AbilityEligibility` формируют запись рекомендации с `spellID`, текстурой, именем, привязкой клавиши, приоритетом и каналом; игровой каст или нажатие не выполняются.
- [`KordRotation/Core/ActionBarScanner.lua`](KordRotation/Core/ActionBarScanner.lua): назначение модуля — чтение слотов панели, а не их нажатие или изменение.
- [`KordRotation/Core/BindingResolver.lua`](KordRotation/Core/BindingResolver.lua): чтение назначенных клавиш без `SetBinding` или симуляции нажатия.
- [`KordRotation/Core/SafeActions.lua`](KordRotation/Core/SafeActions.lua): `Run` и `Flush` выполняют переданные callback вне боя либо откладывают их до `PLAYER_REGEN_ENABLED`. В самом модуле нет каста, макроса или смены цели. **Однако произвольность callback требует отдельной проверки всех мест вызова `SafeActions:Run`: само имя SafeActions не доказывает безопасность любого переданного действия.**
- Проверены тексты `GameAPI.lua`, `SafeActions.lua`, `RotationDisplay.lua`, `SpellIcon.lua`, `MainWindow.lua`, `RotationEngine.lua`, `BindingResolver.lua`, `ActionBarScanner.lua` на прямые вызовы `CastSpell`, `UseAction`, `RunMacro`, `TargetUnit`, `SetAttribute`, `SecureActionButton`, `SetBinding` и команды `/cast`, `/target`: совпадений не обнаружено.

### Вердикт

**РЕАЛИЗОВАНО — по проверенным центральным модулям исправления не требуются.**

Это **не** заявление о завершённом полном аудите каждого Lua-файла: не проверены все профили, UI-страницы, DevTools и все места передачи callback в `SafeActions`. Для окончательного утверждения «во всём аддоне отсутствуют исполняющие игровые действия» требуется полный обход файлов и вызовов, включая динамические обращения к API.

### Дополнительная проверка

1. Проверить все вызовы `SafeActions:Run` и содержимое передаваемых callback.
2. Проверить остальные Lua-файлы и профили на прямые и косвенные исполняющие API, макросы, смену цели, защищённые атрибуты и симуляцию нажатий.
3. Закрепить read-only инвариант тестом/статическим контролем, который отклоняет добавление запрещённых вызовов.

**Изменения кода:** не выполнялись; добавлена документация.


## PR-04 — Единственный арбитр доступности действия: AbilityEligibility; профиль без игрового API

### Требование

Окончательное решение о пригодности способности к рекомендации (`READY`, `BLOCKED`, `UNKNOWN`) принимает только `KordRotation/Core/AbilityEligibility.lua`. Условия профиля могут определять **желательность и приоритет**, но не объявлять способность готовой самостоятельно. Профиль получает только ограниченный интерфейс условий `S` и конфигурацию; не вызывает игровой API напрямую, в том числе через `KR.GameAPI`, `_G` или обходные обёртки. Чтение книги заклинаний и локализованных названий должно выполняться отдельным провайдером/каталогом до передачи данных профилю.

### Проверка исходников Kord (main)

- [`KordRotation/Core/RotationEngine.lua`](KordRotation/Core/RotationEngine.lua), строки 202–253: движок вызывает `rule.when(S,cfg)`; только если условие равно `true`, запрашивает `KR.RotationConditions:Check(S,spellID,policy)`. Статус `READY` берётся из результата проверки пригодности.
- [`KordRotation/Core/RotationConditions.lua`](KordRotation/Core/RotationConditions.lua), строки 152–191, 256–260, 274–312, 341–345: `Check` делегирует `KR.AbilityEligibility.Evaluate`; `spellAvailable` использует тот же модуль; `spellFact` делегирует `KR.AbilityEligibility.Fact`. Непроверенный ответ превращается в `UNKNOWN`.
- [`KordRotation/Core/AbilityEligibility.lua`](KordRotation/Core/AbilityEligibility.lua): отдельный модуль проверяет изученность, cooldown, GCD, ресурсы, дальность и другие условия применимости.
- [`KordRotation/Core/RotationProfiles.lua`](KordRotation/Core/RotationProfiles.lua), строки 149–175 и 217–224: проверяет контракт правил и сохраняет `when` как функцию; ограниченный `S` передаётся движком.
- **Подтверждённое нарушение запрета API в профиле:** [`KordRotation/Profiles/Hunter/BM_Leveling_Contract.lua`](KordRotation/Profiles/Hunter/BM_Leveling_Contract.lua), строки **514–542**, функция `resolveSpells`, напрямую обращается к `KR.GameAPI` и вызывает `ReadValues("GetSpellInfo",...)`, `Read("C_Spell.GetSpellInfo",...)` и `ReadField(...)` для разрешения локализованных названий заклинаний. Это не проверка готовности к применению, но **всё равно нарушает буквальное требование «профиль не обращается к игровому API»**.
- Дополнительно просмотрены профили `Kord_Hunter_BM_60_PVE.lua`, `Kord_Hunter_BM_Leveling_PVE.lua`, `Kord_Hunter_MM_60_PVE.lua`, `Kord_Hunter_MM_Leveling_PVE.lua`, `Kord_Hunter_SV_Core.lua`, `BM_Pilot_Experimental.lua`: аналогичных прямых обращений в проверенных файлах не обнаружено. Строка с `GetSpellInfo` в BM 60 — комментарий, не вызов.

### Вердикт

**РЕАЛИЗОВАНО — НЕОБХОДИМО ИСПРАВИТЬ.**

Единый арбитр `READY` для основной ротации реализован через `AbilityEligibility`. Однако требование полностью не соблюдено: профиль `BM_Leveling_Contract.lua` непосредственно вызывает читающий игровой API через `KR.GameAPI`.

### Требуемое исправление

1. Вынести локализацию и сопоставление рангов из `BM_Leveling_Contract.resolveSpells` в `SpellCatalogue` либо отдельный сервис разрешения заклинаний. Профиль должен получать уже подготовленные значения без вызовов `KR.GameAPI`.
2. Сохранить существующий путь `rule.when → RotationConditions.Check → AbilityEligibility.Evaluate` и запретить самостоятельную выдачу `READY` профилями.
3. Добавить статическую проверку профилей на `KR.GameAPI`, прямые вызовы WoW API и обходные обращения; тестировать, что `UNKNOWN` от `AbilityEligibility` не превращается в `READY`.

**Изменения кода движка:** не выполнялись; обновлена только документация требований.


## PR-05 — Объяснимость каждого решения

### Требование

Для каждой оценки движок должен позволять установить: **действие (какое заклинание/правило рассматривается или выбрано), приоритет, причину выбора, статус**. При отказе (`BLOCKED`, `UNKNOWN`, `UNAVAILABLE`, `ERROR`) должна сохраняться конкретная причина отказа, а не только отсутствие рекомендации. Диагностика должна позволять связать решение с правилом и результатами проверок, не раскрывая защищённые игровые значения. Не следует выдавать «полностью объяснимо», если причина доступна лишь как общий код `none` или `condition_false` без идентификатора правила и контекста.

### Проверка исходников Kord (main)

- [`KordRotation/Core/RotationEngine.lua`](KordRotation/Core/RotationEngine.lua), строки 6–12: `unknown` и `blocked` сохраняют `status`, `reason`, `profileID` и `diagnostics`.
- `RotationEngine.lua`, строки 184–238: на каждом реально пройденном приоритете формируются `status` и код `reason` (маршрутизация, режим, отключение, ошибка условия, `UNKNOWN`, отказ `AbilityEligibility`). Строки 231–234 сохраняют `{priority=i,status=status,reason=reason}`, при наличии — `checks` и `barReason`.
- **Подтверждённый пробел успешного решения:** `RotationEngine.lua`, строки 239–252: в `queue[1]` передаются `spellID`, имя, `priority`, категория, режим, канал и другие поля, но **нет `reason` или идентификатора правила `rule.id`**. Успешный `READY` в диагностике может иметь `reason=nil` (см. `AbilityEligibility.lua`, строки 381–387), поэтому явное «почему именно это действие» не закреплено в итоговой записи.

## PR-06 — Единый адаптер игрового API с белым списком и безопасным отсутствием функций

### Требование

Все вызовы игрового API, используемые для чтения состояния и принятия решений, должны проходить через **один** адаптер `GameAPI` с явным белым списком. Если функция отсутствует или не поддерживается клиентом, вызов не должен приводить к необработанной ошибке: адаптер возвращает `UNAVAILABLE`/`UNKNOWN`, а логический потребитель получает `nil` (не `false` и не `0`). Не разрешать обход через прямые `_G`-вызовы, динамические имена или локальные дубли адаптера. Разрешённые операции UI (создание фреймов, подписка на события) следует отделять от игрового API наблюдения.

### Проверка Kord (исходники main)

- [`KordRotation/Core/GameAPI.lua`](KordRotation/Core/GameAPI.lua), строки 8–56: явный список разрешённых имён чтения, в том числе `UnitExists`, `UnitGUID`, `GetSpellInfo`, `C_Spell.*` и `InCombatLockdown`.
- `GameAPI.lua`, строки 60–70: `resolve` разрешает только имя из белого списка; отсутствующий глобальный объект или метод возвращает `nil`.
- `GameAPI.lua`, строки 114–191: `Read`, `ReadTuple`, `ReadValues` используют `pcall`; отсутствующая функция даёт `UNAVAILABLE/api_missing`, ошибка вызова — `ERROR/api_call_failed`, секретный или отсутствующий результат — `UNKNOWN`. Для потребителя это означает **неизвестное значение (`nil`) после преобразования статуса**, а не буквальный `nil` на выходе `GameAPI:Read`, который возвращает структурированную запись.
- [`KordRotation/Core/GameState.lua`](KordRotation/Core/GameState.lua), строки 24–40: обёртки `read`, `tuple`, `number` используют `KR.GameAPI`; отсутствующие данные остаются неопределёнными.
- [`KordRotation/Core/SpellCatalogue.lua`](KordRotation/Core/SpellCatalogue.lua), строки 17–35: чтение книги заклинаний делегировано `KR.GameAPI`.
- [`KordRotation/Core/ActionBarScanner.lua`](KordRotation/Core/ActionBarScanner.lua), строки 27–60: основные операции чтения слотов и времени используют `KR.GameAPI`.
- **Подтверждённый обход:** [`KordRotation/Core/SafeActions.lua`](KordRotation/Core/SafeActions.lua), строки 6–12: `combat()` напрямую проверяет наличие и вызывает глобальную `InCombatLockdown` через `pcall`, минуя `KR.GameAPI`. Отсутствие функции здесь безопасно приводит к `nil`, однако нарушается требование единственного адаптера.
- **Внутреннее исключение самого адаптера:** `GameAPI.lua`, строки 95–103, `safeTime()` напрямую получает `_G.GetTime` для служебного `observedAt`. Это находится **внутри** адаптера и не является обходом со стороны потребителя, но должно быть документировано как внутренний служебный путь.
- **Граница аудита:** проверены указанные ключевые модули, но не все UI/DevTools/профили и не все динамические вызовы. Полное отсутствие других обходов не доказано.

### Вердикт

**РЕАЛИЗОВАНО — НЕОБХОДИМО ИСПРАВИТЬ.**

Белый список и безопасная обработка отсутствующего API присутствуют. Подтверждён обход центрального адаптера в `SafeActions.combat()`. При этом нельзя говорить, что `GameAPI:Read` буквально возвращает `nil`: он возвращает структурированный статус, который должен превращаться в `nil` на уровне значения условия.

## PR-07 — Изоляция ошибок профилей и провайдеров: ошибка → UNKNOWN, не READY

### Требование

Исключение в условии профиля, провайдере данных или проверке пригодности способности не должно прерывать работу аддона и не должно трактоваться как разрешение действия. Граница исполнения должна использовать `pcall` (либо эквивалентную защищённую оболочку); ошибка, неверный контракт или отсутствие достоверных данных преобразуются в `UNKNOWN`/`nil`. Нельзя молча продолжать к более низкому приоритету, если неизвестный более высокий приоритет может изменить выбор. Для диагностики сохраняется безопасный код причины без небезопасного текста ошибки.

### Проверка Kord (исходники main)

- [`KordRotation/Core/RotationEngine.lua`](KordRotation/Core/RotationEngine.lua), строки 202–211: `pcall(rule.when,S,cfg)` изолирует исключение профиля; ошибка даёт `UNKNOWN/condition_error`, а не `READY`. Строки 258–265 и 300–303: весь расчёт `run` дополнительно защищён `pcall`, ошибка даёт `UNKNOWN/engine_exception`.
- [`KordRotation/Core/RotationConditions.lua`](KordRotation/Core/RotationConditions.lua), строки 116–130: `pcall(GameState.ReadSignal,...)`; ошибка провайдера превращается в `nil` с причиной `signal_provider_error`. Строки 167–190: `pcall(AbilityEligibility.Evaluate,...)`, неверный ответ — `UNKNOWN/eligibility_unverified`. Строки 295–310: `pcall(AbilityEligibility.Fact,...)`, неуспешное чтение факта не превращается в `true`.
- [`KordRotation/Core/RotationAudit.lua`](KordRotation/Core/RotationAudit.lua), строки 90–114, 141–143: ошибки `rule.when` и общего аудита изолируются, результат `UNKNOWN`.
- [`KordRotation/Core/AbilityEligibility.lua`](KordRotation/Core/AbilityEligibility.lua), строки 347–385: проверяющие функции `castStatus`, `usability`, `charges`, `cooldown`, `gcd`, `targetAndRange` вызываются непосредственно как `entry[2](...)`, **без отдельного `pcall` для каждой проверки**. Если одна из них бросит исключение, оно будет перехвачено верхним `pcall` в `RotationConditions.eligibility` для стандартного пути движка, и итог не станет `READY`; однако локальная причина и список пройденных проверок потеряются, а прямой вызов `AbilityEligibility:Evaluate` не имеет такой же гарантии локальной изоляции.
- `RotationEngine.lua`, строки 235–238: при `reason=="condition_unknown"` и `rule.onUnknown=="skip"` движок продолжает к нижнему приоритету. **Это не относится к `condition_error` (ошибка профиля останавливает выбор), но может нарушать общий запрет превращать неопределённость в достоверную нижестоящую рекомендацию.** Проверить применение политики `skip` отдельно.
- [`KordRotation/Core/GameAPI.lua`](KordRotation/Core/GameAPI.lua), строки 114–191: `pcall` вокруг игрового API; отсутствующий/нечитаемый ответ не выдаётся как достоверный.

### Вердикт

**РЕАЛИЗОВАНО — НЕОБХОДИМО ИСПРАВИТЬ.**

Главный путь `rule.when → GameState/AbilityEligibility → RotationEngine` защищён и не превращает исключение в `READY`. Но локальная изоляция каждой проверки внутри `AbilityEligibility` отсутствует, а для политики `onUnknown="skip"` требуется доказательство безопасного пропуска. Полное покрытие всех сторонних потребителей `AbilityEligibility` и всех провайдеров ещё не доказано.

### Требуемое исправление

1. В `AbilityEligibility.Evaluate` защищать каждый вызов проверяющей функции через `pcall`; при исключении выдавать `UNKNOWN` с фиксированной причиной `eligibility_check_error` и именем этапа, сохраняя безопасную диагностику.
2. Проверить все прямые вызовы `AbilityEligibility` и провайдеров вне основного пути на локальную защиту; исключения не должны выходить наружу и не должны превращаться в `READY`.
3. Проаудировать все правила с `onUnknown="skip"`; не разрешать пропуск неизвестного более высокого приоритета без явно доказанной безопасности.
4. Добавить тесты исключений в `rule.when`, `GameState.ReadSignal`, `AbilityEligibility.Evaluate`, в каждой внутренней проверке пригодности и при ошибках внешнего игрового API. Ожидаемый итог — `UNKNOWN` и код причины, никогда ложный `READY`.

**Изменения кода:** не выполнялись; добавлена запись аудита.

**Приоритет: P0.**

### Требование

**ЧАСТИЧНО РЕАЛИЗОВАНО — ТРЕБУЕТСЯ ДОРАБОТКА (P0).**

Безопасное чтение текущего/максимального здоровья и расчёт процента из двух подтверждённых чисел присутствуют. Нет доказанного интегрированного резервного процентного источника для защищённых чисел; интерфейс профиля не предоставляет текущего и максимального здоровья отдельно.

## Обязательный формат дальнейших аудитов PL и последующих пунктов

Для **каждого** нового пункта требований после проверки реализации Kord обязательно включать раздел **«Как реализовано в референсах»** с **отдельным** разбором каждого применимого предоставленного референса: `Sonah`, `JustAC`, `ForeverAuras`, `MaxDps`, `ForeverRotation`, `RotationGuide`, `RotationMaster`. Для каждого указывать фактический механизм (конкретные файлы/функции/условия и особенности обработки неизвестных данных), а не предположение или совет «как референс рекомендует». Если функция не найдена или анализ невозможен, прямо фиксировать **«не обнаружено в проверенных файлах»** или **«не проверено»**, не выдумывать реализацию.

После сравнения обязательно включать раздел **«Моя рекомендация»**: выбрать предпочтительный подход из конкретного референса либо обоснованную комбинацию, объяснить почему именно этот метод подходит Kord (безопасность secret, тристейт, единый GameAPI, стоимость вычислений, совместимость с клиентом), а также отметить, что именно не стоит переносить. В пользовательском ответе обязательно кратко отражать реализацию **каждого** референса и собственный выбор; одной общей фразы «сравнил с референсами» недостаточно.

Этот формат действует **для всех последующих пунктов**. Ранее внесённые пункты PL-01–PL-03 не считать полноценно сопоставленными с каждым референсом без отдельного повторного аудита. Сам по себе этот раздел не означает изменения кода аддона.


## PL-04 — Ресурсы игрока: мана, ярость, энергия, фокус (если поддерживается)

**Приоритет: P0.**

### Требование

Наблюдать для каждого доступного типа ресурса `current`, `maximum`, `percent` с явным типом и статусом достоверности. Отличать активный ресурс (`UnitPowerType`) от явно запрошенного ресурса (мана/ярость/энергия/фокус): отсутствие типа у данного класса/формы не означает нулевой запас. Не вычислять процент при `maximum<=0`, ошибке API или secret. Не переносить защищённые значения в арифметику и сравнения; `UNKNOWN` не означает `false` или `0`.

### Аудит Kord (main)

- [`KordRotation/Core/GameState.lua`](KordRotation/Core/GameState.lua), строки 80–104: `cleanPower()` получает только **текущий активный** `UnitPowerType("player")`, затем `UnitPower` и `UnitPowerMax` с этим типом. При подтверждённых числах и максимуме >0 рассчитывает процент; при неизвестном типе/значении не подставляет ноль. При `maximum==0` и `current==0` процент отсутствует.
- `GameState.lua`, строки 229–243: снимок содержит одну запись `resources`, а не отдельные `mana`, `rage`, `energy`, `focus`. Поэтому, например, вторичная мана при активной энергии не наблюдается этим путём.
- [`KordRotation/Core/GameAPI.lua`](KordRotation/Core/GameAPI.lua), строки 8–18, 114–135, 257–267: белый список разрешает `UnitPowerType`, `UnitPower`, `UnitPowerMax`, `UnitPowerPercent`; `Read` защищён `pcall` и проверяет secret до арифметики. `ReadPowerPercent` требует подтверждённый тип и curve; автоматически в `cleanPower` не применяется.
- [`KordRotation/Core/RotationConditions.lua`](KordRotation/Core/RotationConditions.lua), строки 7–27: доступен только `resources.percent` активного ресурса, без адресации четырёх типов и отдельных current/max.

### Как реализовано в семи референсах (проверены локальные архивы)

1. **Sonah** — `Sonah/Core/Atoms/Units.lua`, строки 325–352: `Units.Power`/`PowerMax` читают через `Secret.CallNumber`; `PowerPercent` сначала считает `current/max*100`, затем пробует `UnitPowerPercent`, при недоступности возвращает `nil`. 2. **JustAC** — `JustAC/SpellQueue.lua`, строки 1172–1185: пороги ресурса SimC преобразуются из абсолютных единиц в проценты по `UnitPowerMax("player",pt)`, с проверкой максимума и secret; `BlizzardAPI/StateHelpers.lua`, строки 693–716: пороговая кривая и `pcall(UnitPowerPercent,...,curve)` позволяют проверять условие без чтения обычного числового процента. `UI/UIHealthBar.lua`, строки 1022–1023: отдельные сырые чтения текущего и максимального ресурса для UI.
3. **ForeverAuras** — `ForeverAuras/Prototypes.lua`, строки 3719–3767, 3940: универсальные триггеры получают тип, `UnitPower` и `UnitPowerMax`, вычисляют процент только если значения не secret и максимум ненулевой, иначе используют `UnitPowerPercent` с кривой; `Conditions.lua`, строки 550–560: кривые для условных проверок; `ForeverAurasOptions/TriggerSecretWarnings.lua`, строки 85–105: отдельные предупреждения о secret-ограничениях для power.

**Основа — RotationMaster**: кэшируемый за оценку типизированный провайдер с `nil + reason` и отдельный путь пороговых кривых для secret-режима. **Дополнить явным выбором ресурса из Sonah/MaxDps**: `mana`, `rage`, `energy`, `focus` должны адресоваться по проверенному power-type ID независимо от активного типа, когда клиент поддерживает этот ресурс. Не копировать прямую арифметику над secret из MaxDps, ложное `false` из эвристики RotationGuide и передачу secret-значений UI как обычных чисел в условиях.

### Вердикт

**ЧАСТИЧНО РЕАЛИЗОВАНО — НЕОБХОДИМО ДОРАБОТАТЬ (P0).**

Безопасный снимок активного ресурса есть, но независимых записей для маны, ярости, энергии и фокуса нет; пороговый secret-safe путь не интегрирован.

5. Добавить тесты переключения типа, каждого из четырёх ресурсов, нулевого максимума, `current>maximum`, отсутствующего API, secret и корректной инвалидации кэша.

### Вердикт

**НЕ РЕАЛИЗОВАНО КАК ОТДЕЛЬНАЯ СИСТЕМА — НЕОБХОДИМО ДОРАБОТАТЬ (P0).**

### Как делают семь референсов (проверены локальные ZIP)

1. **Sonah** — `Sonah/Core/Atoms/Talents.lua`: прямо учитывает отсутствие classic `GetTalentInfo` на Forever; получает активный `C_Traits` config и данные entry/node, разделяет статическую карту и живые `NodeState`/`LiveRank`/`LivePointsInTree`, защищает чтения через `Secret`. `Sonah/Core/Molecules/Conditions.lua:1204–1205`: `C.talent(name,rank)` сравнивает индивидуальный ранг с порогом. Подход полезен для соответствия ID, но импортный слой Kord не нужен.
3. **ForeverAuras** — `ForeverAuras/Prototypes.lua:740–797`: обходит `C_Traits.GetNodeInfo`, `GetEntryInfo`, получает `activeEntry`, `ranksPurchased`, связывает talentID/spellID/ранг и даёт триггеры выбранности. `ForeverAuras/Types_Forever.lua:96–179` адаптирует дерево Forever. Сильная сторона — правильное различение node/entry/выбранного варианта.

5. **ForeverRotation** — по проверенному поиску Lua не обнаружены `GetTalentInfo`, `C_Traits.GetNodeInfo` и индивидуальный talent-провайдер. Комментарий `Engine.lua:916` упоминает изменение таланта/ранга, но это не реализация чтения талантов.

Это наиболее подходящая архитектура условий и платформенного чтения.

## 2. Заклинания и способности

### SP-01 — Известно ли заклинание (книга, талант, руна). Отсутствие в каталоге — не доказательство незнания

**Приоритет: P0.**

#### Требование

Для конкретного spellID установить `known=true/false/UNKNOWN` с источником и причиной. Источники: книга игрока, подтверждённое изучение через талант, активная руна/гравировка WoW Forever и независимый API `C_SpellBook.IsSpellKnown` (при наличии). **Отсутствие в перечисленном каталоге не доказывает незнание**; отрицательный результат допустим только при достоверном отрицательном ответе подходящего API либо исчерпывающей проверке применимого источника с подтверждённым контрактом. Разделять известность, пассивность, доступность в форме, usability, cooldown и право `AbilityEligibility` выдать READY. Учитывать ранги и заменяющие/override spellID, player/pet banks, secret и несовместимость клиентских API.

#### Аудит Kord (main)

- [`KordRotation/Core/SpellCatalogue.lua`](KordRotation/Core/SpellCatalogue.lua), строки 52–182, 209–252: есть безопасный ограниченный обход legacy/modern книги, ID-ключи, отказ публиковать частично просканированный каталог, инвалидация по `spellbook/talents/identity`. Каталог не является исчерпывающим перечнем талантных/рунических заклинаний.

Нельзя считать эту зависимость обязательной.

- [`KordRotation/Core/Talents.lua`](KordRotation/Core/Talents.lua), строки 85–166: читаются `C_Traits` и суммы рангов, но индивидуальные spellID/choice-node наружу не предоставляются (см. PL-13).

#### Как делают семь референсов (проверены локальные ZIP)

1. **Sonah** — `Sonah/Core/Atoms/Spells.lua:84,150–196`: сначала сопоставляет изученные ID/ранги и имена в книге; затем **специально** вызывает `C_SpellBook.IsSpellKnown(id, PlayerBank)` для талантных/пассивных способностей, которые никогда не попадают в книгу; `IsPlayerSpell` — устаревший fallback. Использует `Secret.Call` и проверяет варианты ID. Это прямое подтверждение принципа SP-01.
2. **JustAC** — `JustAC/GapCloserEngine.lua:70–103`: для form-gated способности проверяет `IsSpellKnown`, а не `IsSpellAvailable` (иначе известное заклинание ошибочно исключается из-за текущей формы); отдельно исключает пассивные. `JustAC/BlizzardAPI/SpellQuery.lua:106–133` проверяет пассивность через spell API и `FindSpellBookSlotForSpell`/информацию записи. Источники известности и применимости разделены.
3. **ForeverAuras** — `ForeverAuras/GenericTrigger.lua:2634,2724,2984` вызывает `WeakAuras.IsSpellKnownIncludingPet(effectiveSpellId)`; учитывает эффективный spellID и банк питомца в системе триггеров. Полноценного подтверждённого объединения с активными рунами/гравировками в этих местах нет.
4. **MaxDps** — `MaxDps/Helper.lua:2538–2543,2589`: использует `IsSpellKnownOrOverridesKnown(spell)`, отдельно проверяет `C_Spell.IsSpellUsable` и cooldown; для некоторых нерозничных клиентов проверяет слоты способностей питомца. Прямой булевый gate и клиентские предположения не заменяют тристейт-провайдер.
5. **ForeverRotation** — `ForeverRotation/Core.lua:153–161`: `ns.known(name)` разрешает ID по имени и вызывает `C_SpellBook.IsSpellKnown` через `pcall`, кэширует `false` даже при неудаче API. Это простой known-gate, но `UNKNOWN` теряется; нельзя копировать в Kord.
6. **RotationGuide** — `RotationGuide/Core/State.lua:27–55`: строит карту книги `name → highest rank spellID` через `C_SpellBook.GetSpellBookItemInfo`, исключая пассивные записи; в проверенном механизме не обнаружено независимого доказательства известных талантных/рунических заклинаний вне книги. Отсутствие в карте нельзя трактовать как незнание.
7. **RotationMaster** — `RotationMaster/Platform/spells.lua:286–342`: `Platform:IsSpellKnown(spellID,pet)` валидирует ID/банк, предпочитает `C_SpellBook.IsSpellKnown` с Player/Pet enum, fallback на legacy `IsSpellKnown`; `pcall`, проверка secret и типа, `nil,reason` при недостоверности. `RotationMaster/Conditions/known_spell.lua:4–53`: отдельное условие known вызывает платформенный адаптер, не WoW API напрямую. Не доказано, что это само по себе охватывает активные гравировки Forever.

#### Сравнение и моя рекомендация

**Основа — RotationMaster + Sonah**, дополнить идеей JustAC: 
- RotationMaster даёт наиболее подходящий платформенный тристейт-контракт `known/unknown+reason`, player/pet banks и проверку secret.
- Sonah явно решает проблему «заклинание изучено через талант/пассивность, но отсутствует в книге» и умеет сопоставлять ID/ранги.
- JustAC демонстрирует, почему нельзя смешивать известность с текущей доступностью по форме и почему пассивность — отдельный фильтр.
- Для рун/гравировок требуется отдельный **достоверный** провайдер `C_Engraving` по PL-05; ни один из приведённых known-gate сам по себе не доказывает его наличие.

Не копировать `api error → false` из ForeverRotation, `catalogue absence → false` из упрощённых карт и прямые WoW API в профили.

#### Вердикт

**ЧАСТИЧНО РЕАЛИЗОВАНО — ИСПРАВИТЬ (P0).** Главный принцип «нет в каталоге ≠ не изучено» уже заложен, но есть преждевременный `UNKNOWN` при недоступном каталоге, не хватает независимого talent/rune evidence и проверки соответствующих spellID.

#### Требуемые изменения

1. Перестроить `AbilityEligibility.spellKnown`: не требовать `catalogue.ready` для независимого `C_SpellBook.IsSpellKnown`; использовать каталог как положительное свидетельство, а не обязательный gate.

3. Интегрировать индивидуальные таланты PL-13 и активные гравировки PL-05, не приписывая изучение по одному наличию spellID в базе.
4. Разделить known, passive, usability, form gating, cooldown, rune activation и окончательную eligibility; профили запрашивают факты через `Needs` и `RotationConditions`.
5. Кэшировать на проход, инвалидировать по `SPELLS_CHANGED`, `LEARNED_SPELL_IN_TAB` (если поддерживается), смене талантов, рунических гравировок, специализации, конфигурации и банка питомца.
6. Тесты: книга содержит ID; книга не содержит ID, но known-API true; каталог недоступен, known-API true; талантный spell вне книги; активная/неактивная руна; highest rank и override; пассивная способность; form-gated известная способность; player/pet bank; secret/ошибка/отсутствующий API; конфликт свидетельств.

### SP-02 — Ранги: найти максимально выученный ранг по семейству ID

**Приоритет: P0.**

#### Требование

Для заданного семейства spellID определить **максимальный действительно изученный ранг**, его spellID, номер ранга, источник и достоверность. Семейство должно быть явно проверенным набором рангов/замен с устойчивыми ID: совпадение локализованного имени или числовой порядок spellID **не доказывают** родство и ранг. Отличать «максимальный ранг, наблюдённый в книге» от «максимальный изученный ранг»; талантные, рунические, пассивные, pet и override-версии требуют отдельной проверки. Неизвестный ранг, частичная книга, secret или недоступная проверка более высокого ранга → `UNKNOWN`, а не заведомо максимальный из видимых.

#### Аудит Kord

- [`KordRotation/Core/SpellCatalogue.lua`](KordRotation/Core/SpellCatalogue.lua), строки 48–67: **уже сохраняет отдельные spellID для рангов** и поля `rank`/`rankNumber`; номер пытается извлечь из подписи ранга. Это полезный сырой источник, но не доказательство полноты семейства.
- `SpellCatalogue.lua`, строки 94–125, 152–182: legacy/modern обход книги; в modern-ветке номер ранга берётся из `subName` при наличии. В строках 194–195 сортировка учитывает `rankNumber`, но **нет индекса `familyID → highest learned spellID`**.
- [`KordRotation/Core/AbilityEligibility.lua`](KordRotation/Core/AbilityEligibility.lua), строки 47–71, 293–294, 415–428: проверяет **переданный** spellID, не выбирает автоматически максимальный изученный ранг. Преждевременная зависимость от `catalogue.ready` отмечена в SP-01.
- [`KordRotation/Core/GameAPI.lua`](KordRotation/Core/GameAPI.lua): доступен `C_SpellBook.IsSpellKnown`, но нет семейного провайдера рангов и подтверждённой карты `baseID → rankIDs`.
- Существующий `Talents.lua` возвращает суммы рангов деревьев, не индивидуальные spellID/ранги; рунический провайдер не реализован (PL-13/PL-05).

#### Как делают семь референсов (проверены локальные ZIP)

1. **Sonah** — `Sonah/Core/Atoms/Spells.lua:150–196`: формирует карту известных spellID/рангов из книги, сохраняет highest-rank по имени и сверяет с независимым `C_SpellBook.IsSpellKnown` для отсутствующих в книге талантных/пассивных заклинаний; `Sonah/Core/Atoms/Spells.lua:84` учитывает версии ID. Преимущество — явное отделение известности от книги, недостаток — сопоставление по имени может быть неоднозначным.
2. **JustAC** — `JustAC/BlizzardAPI/SpellQuery.lua:244–280`: сканирует книгу и сопоставляет spellID/ранги; `JustAC/RotationImport.lua:147` обрабатывает таланты отдельно. В проверенном коде нет подтверждённого полного familyID-реестра всех рангов WoW Forever; не принимать имя за уникальное семейство.
3. **ForeverAuras** — `ForeverAuras/GenericTrigger.lua:2519–2562`: использует spellbook lookup и данные рангов для триггеров, с выбором spellID/эффективного ID; это механизм универсальных триггеров, а не подтверждённый полный family-max provider. Классовые ранги из талантов/гравировок требуют отдельного источника.
4. **MaxDps** — `MaxDps/Helper.lua:2538–2543`: `IsSpellKnownOrOverridesKnown` подтверждает знание ID или override, но **не определяет максимальный ранг семейства**; профили часто используют заранее заданные spellID. В проверенном коде нет общего family-max провайдера.
5. **ForeverRotation** — `ForeverRotation/Core.lua:153–161`: `ns.known(name)` проверяет известность разрешённого по имени ID; отдельного надёжного family-max ранжирования в проверенных файлах нет.
6. **RotationGuide** — `RotationGuide/Core/State.lua:27–55`: при обходе книги строит `name → highest rank spellID`, сравнивая числовые ранги; полезный простой алгоритм выбора, но **локализованное имя не гарантирует стабильное ID-семейство**, а отсутствие в книге не доказывает незнание.
7. **RotationMaster** — `RotationMaster/Platform/spells.lua:286–342`: защищённый `IsSpellKnown` для конкретного ID с player/pet bank, `nil,reason` при недоступности; `RotationMaster/Platform/spellbook.lua` сканирует записи книги и их ранги. Платформенное разделение подходит для Kord, но универсальный исчерпывающий `family → max rank` для талантов/гравировок в проверенных местах не подтверждён.

#### Сравнение и моя рекомендация

**Основа — Sonah + RotationMaster; алгоритм выбора из RotationGuide только внутри подтверждённого ID-семейства.** Sonah полезен независимым known-API для талантных/пассивных рангов; RotationMaster — secret-safe платформенной проверкой каждого ID и различением `UNKNOWN`; RotationGuide — идеей выбрать максимальный подтверждённый ранг, но не его ключом по имени. **Ключевая собственная доработка Kord:** статический валидированный реестр `SpellRankFamilies` (familyKey, ordered `{spellID,rank,sourceKind}`, class/variant, возможные override) и ленивый `HighestLearnedRank(familyKey)`. Проверять от старшего ранга к младшему, но при `UNKNOWN` для более высокого ранга нельзя утверждать, что младший — абсолютный максимум. Не предполагать, что больший spellID означает больший ранг. Не копировать слепую подстановку `rank=0` при secret.

#### Вердикт

**ЧАСТИЧНО РЕАЛИЗОВАНО — ТРЕБУЕТСЯ ДОРАБОТКА (P0).**

Сканирование книги и метаданные рангов уже есть; нет достоверного семейного реестра, выбора максимального изученного ранга и покрытия талантов/гравировок.

#### Требуемые изменения

1. Создать `SpellRankFamilies` с явно упорядоченными проверенными ID рангов; учесть class, pet, talent, rune, override и версию WoW Forever. Не использовать имя как единственный идентификатор семейства.
2. Реализовать ленивый `HighestLearnedRank(familyKey)` через SP-01 `SpellKnowledgeObservation`: статус `READY` только если максимальность доказана, `UNKNOWN` при неизвестных старших рангах, `BLOCKED` если подтверждено отсутствие всех применимых рангов.
3. Возвращать `spellID`, `rankNumber`, `familyKey`, `status/reason/source` и возможный `overrideID`; не терять отдельные ранги каталога.
4. Интегрировать выбор максимального ранга с `AbilityEligibility` и профилями, не меняя право выдачи итогового READY. Ранг для лечения питомца/аур выбирать по реально изученному максимальному spellID, не по минимальному ID.
5. Инвалидировать по изменениям книги, талантов, рун/гравировок, активного билда, питомца; кэшировать в рамках оценки.
6. Тесты: изучены ранги 1–3; изучен только первый; старший ранг secret; каталог неполон; одинаковые локализованные имена разных семейств; pet rank; талант/руна; override; неизвестный familyKey; смена билда и изучение нового ранга.

**Изменения кода:** не выполнялись; внесён аудит SP-02.
